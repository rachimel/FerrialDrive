## 2. 툴 선행 개발과 시각 검증

- 초기에 게임보다 직접 사용할 제작 툴부터 검증하기로 했다.
- Blender MCP로 메카 모델과 Live2D 표정 리그를 시험했다. 메카 모델 요청에 동작까지 추가한 것은 범위를 넓힌 작업이었고, 사용자는 부자연스러운 동작을 지적했다.
- Live2D 표정은 단순 페이드에서 실제 메시·마스크 보간으로 발전했다. 같은 화풍의 표정 파츠와 중간 자세, 마스크·투명도의 역할 구분이 중요했다.
- 당시 느린 재생은 구간별 측정 후 프레임 제한 대기가 주요 원인으로 보고됐다. 당시 정상 재생 약 60 FPS 기록은 **현재 게임 성능의 보장으로 사용하지 않는다**.
- 표정 스튜디오에 시간·형태 곡선 편집, 저장·복원, 실제 모델 미리보기와 MOC3 출력을 추가했다. 현행 경로는 `Tools/portrait_editor/`다.
- 별도 `live2d-editor`는 정리했다. 수동 PNG 분리·PSD 출력 대신 AI에 추출 위치를 알려주는 대략적인 영역 마스크 흐름을 채택했다. 마스크 자체가 정밀 파츠나 추출 완료 결과는 아니다.
- 기존 Blender 연결은 `Tools/blender_pipeline/`에 유지한다. 현재 도구를 범용 전투 애니메이션·스프라이트 제작 툴로 간주하지 않는다.

## 3. 게임 방향과 저장소·발표자료

- 이름은 **Ferrial Drive**. Python·Pico2D 기반 2D 실시간 메카 액션 RPG다.
- JRPG식 3/4 Top-Down, 군사·산업 Cybernetic SF, 투박한 인간형 메카를 지향한다.
- 전투 참고작은 아머드 코어 6·발드 스카이·환세취호전. 전투 준비 UI/UX는 Baldr 시리즈를 참고한다.
- 발표용 PPT와 상세 기획서 PPT는 별개다. 공개용 자료에서 AI 콘셉트 이미지를 제외했다.
- 공개 저장소는 `https://github.com/rachimel/FerrialDrive`다. AI 생성 이미지·모델과 가공 에셋은 공개 Git에서 제외하며, `data/`·`output/` 등은 로컬에 보관한다.
- 아트는 **기존 그림체 레퍼런스 → JANIMA 레퍼런스 생성 → GPT 수정·정리**를 기준으로 한다. LoRA 학습·데이터 선별은 과거 검토 기록이며 현행 제작 방향이 아니다.
- 다음 주 첫 시연이라는 이야기가 있었으나, **다음 주 전체 기능 시연이라는 해석은 사용자가 정정**했다. 현재 작업을 그 오해에 맞춰 축소하지 않는다.

## 4. 전투 기획의 현재 요약

세부 경계 조건과 수치는 [PRE-PRD](../Ferrial_Drive_PRE_PRD_v0.1.md)를 따른다. 아래 내용은 구현 완료 기능이 아니다.

- 기본 무기는 카타나·기관단총. 탄창은 45발이고, 일반 상태부터 예비 탄약은 무한이며 빈 탄창은 자동 재장전한다.
- 로드아웃은 근접·원거리 한 쌍으로 최대 2세트. F는 세트 내 무기 스왑, E는 잠정 세트 교체 키다.
- WASD 이동·SHIFT 전력 질주, 이동과 마우스 조준은 독립이다. 총은 우클릭 에임·좌클릭 발사, 근접은 좌클릭 공격·우클릭 막기다.
- 근접 3단 콤보에 무기·로드아웃 전환 후 공격도 연계한다. 대시와 무기 전환을 통한 공격 취소는 특정 타이밍에만 허용한다. 일반 대시에는 무적·에너지 비용을 두지 않는다.
- 일반 공격에 자동으로 패리를 붙이던 안은 폐기했다. 양방향 스왑 카운터만 사용하며, 짧은 판정과 쿨타임으로 재시도를 제한한다.
- 근접 카운터는 즉시 제압한다. 대구경탄은 실제 탄을 반사하고 **반사탄이 적에게 명중해야 제압**한다. 파이어볼·바위형 투사체는 카운터 불가, 자동 가드로는 방어 가능하다.
- 작은 탄은 근접 무기 장착 시 확률적으로 튕겨낸다. 우클릭 막기 중 차단 확률을 크게 높이며 자동 가드와는 별도다.
- 원거리 공격은 제압 게이지를 누적하고, 공격이 끊기면 게이지가 서서히 감소한다. 제압·제압 면역 중에는 누적하지 않는다.
- 제압 시간은 추가 공격으로 갱신하지 않는다. 일반 명중으로 제압이 풀리지 않으며 약점 피해 보정도 없다. 해제 후 제압 면역을 부여하고, 면역 적에게 카운터 성공 시 플레이어에게 잠시 무적을 준다.
- Break Assault는 가까운 제압 적에게 별도 입력으로 사용한다. 최대 거리·접촉 가능 여부를 확인하며, 명중하면 제압이 풀려 제압 1회당 한 번만 사용한다. 처치를 보장하지 않는다.
- Break Assault 중에는 피격 가능·동작 중단 없음·소폭 피해 감소. 이후 공격 반대 방향으로 반동 점프하며, 점프 중 조작·피격은 불가다. 주변 전투는 계속 진행하고 슬로는 검토안이다.
- 에너지는 레벨 1~3과 각 게이지로 관리한다. 명중·카운터 회복, 초과 회복 이월, 마지막 회복 후 유예를 둔 자연 감소가 있다.
- 자동 가드는 흡수 피해에 비례해 에너지를 사용한다. 부족한 에너지로 흡수하지 못한 피해는 체력에 적용한다. 고갈 시 꺼지고 회복하면 다시 켜진다.
- 레벨 3 완충 시 Standby 3초, 진입부터 재진입 쿨다운 30초. 대기·예약은 구분하며 완충 대기가 취소돼도 예약은 유지한다.
- Overdrive는 에너지로 유지하고 명중 회복을 허용한다. 시간이 갈수록 소모가 증가하고 레벨 1·게이지 0으로 종료한다. 빠른 연계·재장전, 붉은 외곽·잔상과 불 속성 강화를 구상한다.
- 필살기 연속 베기는 레벨별 7·9·12타, 시전 중 무적이다. 성장은 영구적이고 실패마다 확률 상승과 실패 횟수 천장을 함께 적용한다.
- 필살기 성장 판정은 현재 시전 결과를 반영한다. 레벨업 성공 시 **현재 시전 비용 면제**, 강화된 타수·연출은 **다음 시전부터 적용**한다. 레벨이 올라가도 비용은 유지한다.

## 5. 로제와 훈련 시뮬레이션

- 교관 히로인 이름은 **로제**, 관련 파일명은 `rose`다. 레퍼런스 폴더·이미지와 프롬프트 문서·목록의 이름·참조를 변경했고, 이미지 내용과 Git 제외 상태를 확인했다.
- 교관의 기본 조작 훈련을 거친 뒤 마지막 적 전멸 응용 과제를 수행한다. 반복 연습을 허용하고, 응용 과제 사망 시 해당 과제부터 다시 시작한다.
- 일반형은 근접, 중형은 원거리, 인간형은 복합 역할이다. 응용 과제에서 순차 등장한다.
- 로제의 차가운 질책, 반복 실패·부활 시 시선과 표정 반응은 Live2D 활용 구상이다. 실제 생존을 걱정하는 속마음은 캐릭터 설정이다.
- 위 캐릭터 디테일·실패 반응은 발표자료에서 제외하며, 구체적인 연출은 후속 선택 구현이다. Live2D 연결과 툴 개선을 지금 완료했다고 간주하지 않는다.

## 6. 렌더링·맵·새 제작 툴

- **Pico2D는 필수**, 모듈 원본을 바꾸지 않고 프로젝트에서 함수 연결 지점을 활용하는 방식을 우선 검토한다.
- 사용자는 `SilverMoon`에서 OpenGL 연결을 실증했다고 설명했다. 확인한 현행 코드는 SDL/OpenGL과 Bloom 합성을 사용하고, Pico2D는 번들 폰트 탐색에 쓰인다. 이번 프로젝트의 연결 방식·필수 사용 범위·실제 성능은 미확정이다.
- 3D 모델·맵을 고정 정사영 3/4 시점으로 프리렌더링한다. 광원은 제작 툴에서 조정한 뒤 베이크하고, 그림자를 먼저 그린 뒤 본체를 합성하도록 분리 출력한다.
- 타일은 32 또는 64픽셀 중 미정. 메카의 **화면상 크기는 가로 2타일·세로 3타일**이고 충돌 영역은 별도다. Z값의 용도와 처리 방식은 추후 결정한다.
- 이동 가능 영역은 시각적 타일과 독립 저장하고 장애물 추가·제거 시 갱신한다. **0은 이동 가능, 1은 장애물**이다.
- 필요한 효과는 잔상 투명도·color mix, 실루엣 기반 Rim Lighting, 에너지 Bloom이다. 실루엣 표현이 부족할 때 법선 정보의 추가 출력을 검토한다.
- 기존 Blender MCP 연결을 재사용하고, 새 툴에서 AI의 전투 애니메이션 조작·제작과 사용자 미리보기 확인 후 **8방향 스프라이트 추출**을 지원한다. 범용 툴은 아직 미구현이다.

## 7. 최적화 구상의 정정

- 장애물이 있는 높이층만 저장하는 희소 저장과 높이층별 쿼드트리, 물체 조회용 BVH를 논의했다.
- 한때 도입 예정으로 기록했으나, 사용자는 **실제로 느릴 때 고려할 기술**이라는 의미로 정정했다.
- **현재는 단순하게 구현**하고 성능·메모리 문제가 확인될 때 검토한다. 구조를 미리 구현하는 것을 필수 범위로 잡지 않는다.
- BSP는 이번 범위에서 제외한다. 효과를 판단할 때 조회뿐 아니라 구조 갱신과 메모리 비용도 함께 측정한다.

## 8. UI·애니메이션과 현재 Unit Test

- 기본 텍스트는 에스코어 드림, 굵기 200·300·400은 우선 후보다. 깍두기 도면체는 숫자 전용이 아니라 **HUD용**이다.
- UI 레퍼런스는 배틀필드 3·메탈기어 라이징 리벤전스·에이스 컴뱃·F-15/F-16 HUD. 명일방주의 반응성도 참고 후보로 논의했다.
- 배치·버튼 이름·형태·스타일·폰트는 동작과 분리한다. 표시 문구를 바꿔도 동작 식별자는 유지한다. 구체적인 설정 형식과 편집 방식은 미정이다.
- Ease-In·Ease-Out과 평행이동은 UI와 분리된 공통 애니메이션 계층이 처리한다. 기본 배치와 이동량을 구분하고, 표시와 입력 판정의 최종 위치를 맞춘다.
- 커서에 반응하는 유사 3D 회전·확대·판정 확장은 **가능성을 본 뒤 검토할 후보**다. 필수 구현이나 채택 완료 디자인으로 취급하지 않는다.
- 사용자가 정의한 **Unit Test는 독립 실행할 수 있고 게임에 쉽게 연결될 수 있는 테스트 프로그램**이다. 자동 검사나 수동 관찰 중 어느 한 방식으로 의미를 한정하지 않는다.
- 현재는 **UI 반응성·장면 전환·HUD만 우선 확인**한다. 실제 게임 적용은 미정이다. 테스트용 가짜 데이터와 실행부를 재사용 모듈에서 분리한다.
- 앞서 단순 도형 전투 씬은 첫 교전까지 8개, 전체 전투 규칙은 약 20개 커밋 후보로 논의했다. **이는 구현 완료 수량이 아니며 현재 UI Unit Test보다 먼저 진행하라는 지시도 아니다.**

## 9. 개발 규칙과 남은 결정

- 한국어·간결한 문서와 커밋 메시지, 반말 답변을 사용한다. 클래스명은 대문자로 시작하는 CamelCase, 변수·함수·Python 파일명은 snake_case, 상수는 UPPER_SNAKE_CASE다.
- 들여쓰기 공백 4칸, 시간·거리 단위 명시. 애매한 요구는 추측하지 않고 상의하며, 과도하게 복잡해지면 다른 접근을 검토하고 설계 변경을 상의한다.
- 기능 단위 구현·검증·점진적 커밋을 원칙으로 하고 완료 결과와 미검증 항목을 보고한다.
- UI 설정·편집 방식, 기준 해상도, Pico2D/OpenGL 연결 방식과 성능 목표는 구현 단계에서 확인할 사항이다. 유사 3D·최적화 후보를 필수 구현으로 확대하지 않는다.
- 전투의 미정 입력·판정 시간·확률·비용은 해당 기능을 구현하기 전에 확인한다. 높이·충돌·리깅·프레임 출력 규격도 확정 범위를 넘어 추측하지 않는다.

## 10. 작성 시점의 실제 상태

- 현재 저장소에는 기획 문서, 발표자료와 기존 제작 툴이 있다. **게임 전투 프로토타입과 독립 UI Unit Test 실행 프로그램은 아직 없다.**
- 현재 대화에서는 주로 문서를 보완하고 로제 관련 파일을 정리했다. 실행 환경과 참조 프로젝트를 읽어 확인했으며 새 게임 실행 코드는 작성하지 않았다.
- `docs/발표자료.pptx`는 10쪽 공개용 발표본, `docs/기획서.pptx`는 29쪽 초안이다. 이후 대화에서 보완한 PRE-PRD를 PPT에 다시 동기화하지 않았다.
- 마지막 로컬 커밋은 `5e3c702`의 제압 규칙 확정·히로인 AI 이미지 제외다. 이후 대화에서 수정한 문서·규칙·파일명 변경과 이 로그는 **작성 시점에 미커밋**이다.
- 이전 툴의 테스트·실제 창 검증 기록은 과거 대화의 보고다. 이번 요약 작업에서 게임·툴의 실행 성능이나 시각 품질을 다시 검증하지 않았다.

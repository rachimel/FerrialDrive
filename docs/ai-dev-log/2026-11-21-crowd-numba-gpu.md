# 적 1,000기 교전의 Numba 배치와 GPU 그림자

**기록 ID** `FDLOG-20261121-crowd-numba-gpu`

**범위** 2026-11-20~21 KST. FHD·중간 PBR 무음 교전에서 원거리 본체와 그림자, 근거리 그림자를 검증했다.

## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1)** 적 900~1,000기를 목표로 Numba를 적용한다. 특히 세 번째 병목으로 논의한 적 본체와 그림자를 우선한다.
- **사용자 제안 2 (U2)** GPU가 맡을 수 있는 표시 계산을 우선 옮긴다. 개별 발언의 정확한 시각은 [[FDLOG_MISSING_TIME:FDLOG-20261121-crowd-numba-gpu:U1-U2]]이다. 같은 대화의 `특히 3번`과 `GPU로 던질 수 있는`에서 확인할 수 있다.

## 2. 사용자 제안 중 AI가 수용한 것

- **U1·U2** 같은 포즈를 그릴 때 반복하는 좌표 준비와 제출을 줄였다. 현재 카메라, 근거리·록온 기체 품질과 적 가림 순서를 기준으로 삼았다. 실제 처리 시간과 화면은 별도로 대조했다.

## 3. AI가 제안한 것

- **AI 제안 1 (A1)** 원거리에서는 같은 텍스처가 4회 이상 이어지면 Numba로 SDL 꼭짓점 배열을 채우고 한 번에 그린다. 앞뒤 순서가 바뀌면 겹침이 달라져 본체는 기존 깊이 순서에서 연속한 기체끼리만 묶었다.
- **AI 제안 2 (A2)** 그림자 상자마다 달라지는 여덟 꼭짓점만 전송하고 삼각형의 연결 순서는 GPU 버퍼에 보관한다. 근거리 그림자의 화면 사각형은 기체 발 위치와 포즈당 원본 영역으로 버텍스 셰이더에서 계산한다. 두 제안의 근거는 아래 기능별 커밋과 같은 장면의 계측이다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- 기체 묶음 렌더링, 원거리 공유 프레임과 GPU 우선 검토는 사용자 지시다. 네 기부터 묶는 기준, 인덱스 버퍼와 셰이더 입력 형식은 AI의 구현 결정이다.

## 5. 반영 후 발견한 문제

- **I1** 서로 다른 프로세스에서 잰 프레임 처리 시간의 변동이 컸다. 최종 교차 측정에서도 변경 전 두 실행이 23.67·14.07 FPS로 벌어졌다.
- **I2** 근거리 그림자 셰이더 입력량이 줄어도 이 구간의 시간은 0.89~1.35ms 범위에서 실행마다 순서가 바뀌었다. 전체 1,000기 교전도 60 FPS에 미달했다.

## 6. 사용자 해결 제안과 실제 해결 과정

- **U1 ↔ I1** 원거리 적의 같은 포즈 그림자와 겹침 순서가 맞는 본체를 모아 그렸다. 일반 적의 활동과 가까운 기체의 원래 모션을 유지했다. Numba는 게임 로딩 중 첫 서명을 준비하고, JIT를 사용할 수 없을 때는 기존 개별 복사를 사용한다.
- **U2 ↔ I2** Pico2D의 OpenGL 컨텍스트에서 그림자 삼각형 연결과 화면 배치를 처리했다. 렌더 결과를 게임 규칙으로 되읽는 단계는 추가하지 않았다.

## 7. AI 해결 제안과 실제 해결 과정

- **A1 ↔ I1** 11-20 23:53 KST `c6fc3ae`에서 원거리 그림자를, 23:56 `a32f9c9`에서 본체를 연결했다. 같은 프로세스에서 90프레임당 그림자 배치 대상 11,168개의 CPU 제출 누계는 기존 16.85·18.35ms, Numba 묶음 10.10·13.43ms였다. 전체 본체 그리기 구간은 기존 3.93·6.86ms/프레임, 묶음 3.02·3.23ms/프레임이었다.
- **A2 ↔ I2** 11-21 00:04 KST `16ce2cd`에서 그림자 상자의 인덱스를 GPU에 보관했다. 새 포즈의 꼭짓점 데이터는 소형 5,184→1,152바이트, 중형 4,320→960바이트다. 두 기종·네 모션·여덟 방향·세 시점에서 그림자 192장의 RGB가 모두 일치했다.
- 00:12 KST `e2cf33f`에서 근거리 그림자의 위치와 크기를 셰이더로 옮겼다. 같은 3,291개 배치에서 배열 유니폼 전송량은 157,968→95,248바이트였다. 두 기종·세 모션·세 배율의 화면 18장도 기존 배치와 픽셀이 일치했다.

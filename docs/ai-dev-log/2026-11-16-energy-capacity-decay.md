# 실제 에너지 용량과 회복 후 2초 자연 감소 유예

- **기록 ID:** `FDLOG-20261116-energy-capacity-decay`
- 대화 범위: 2026-11-16 KST, 카메라 12/18px 정정 이후 에너지 자연 감소·실제 용량 지정. 개별 발언 시각은 제공되지 않았다. [[FDLOG_MISSING_TIME:FDLOG-20261116-energy-capacity-decay:scope]] 검색 단서: `에너지는 2초 margin`, `그러면 에너지 총량을 바꿔야지`, `레벨 1 100, 레벨 2 200, 레벨 3 400 오버드라이브 200`.

- 근거: 현재 채팅의 사용자 요청·질문 응답, PRE-PRD 4.3·4.5절, 아래 코드·설정·자동 검사.
- **상태: 명세·코드·설정 반영. 관련 검사 288개 중 285개 통과·선택 GPU 검사 3개 건너뜀·실패 0개. 실제 창·사용감 승인·커밋·업로드 미수행.**

## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1):** 에너지 감소에 2초 margin을 둔다. 현행 명세의 마지막 에너지 회복 이후 유예 규칙에 적용한다.
  - 이유·판단 근거: 유예 시간은 직접 지정했다. 별도의 필요성 설명은 제공되지 않았다. [[FDLOG_MISSING_REASON:FDLOG-20261116-energy-capacity-decay:U1]] 검색 단서: `에너지는 2초 margin 두고, 감소하게` 전후 사용자 발언.
- **사용자 제안 2 (U2):** AI가 현재 정규화 값에 초당 0.5를 직접 적용하면 빠르다고 질문하자, 감소량을 바꾸는 대신 에너지 총량을 바꾸도록 정정했다.
- **사용자 제안 3 (U3):** 각 게이지 용량을 우선 LV1 100·LV2 200·LV3 400·Overdrive 추가 200으로 지정했다. 각 레벨 용량을 묻는 질문에 대한 응답이므로 누적 100/200/400으로 해석하지 않는다. 일반 누적 최대량은 700이다.
- 시각·출처: 현재 채팅의 위 발언과 선택 질문 응답이며, 개별 시각은 TIME(scope)를 따른다.

## 2. 사용자 제안 중 AI가 수용한 것

- U1: 마지막 실제 회복부터 2초를 실제 경과 시간으로 계산한다. 유예를 넘긴 시간에만 기존 기준인 실제 에너지 초당 0.5 감소를 적용한다.
- U2·U3: 실제 에너지 양·레벨별 용량과 화면 비율을 분리했다. 별도 추가 충전량은 일반 에너지 자연 감소로 차감하지 않는다. 기존 감소율을 정규화 게이지의 50%/초로 적용하지 않는다.
- 회복량·스킬 비용·기체별 차등 감소량·Overdrive 전용 소모 곡선의 신규 밸런싱은 이번 범위가 아니다.

## 3. AI가 제안한 것

- **AI의 최초 확인 질문:** 정규화된 레벨당 1과 초당 0.5의 속도를 기준으로 한 레벨을 비우는 시간을 물었다. U2가 실제 용량 변경을 요구하면서 작업 기준을 바로잡았다. 이를 사용자가 감소율 변경을 제안한 것으로 기록하지 않는다.
- **구현상 판단 (A1):** `combat/energy.py`의 실제 에너지 값과 유예 시계를 독립 모듈로 분리하고, 기존 `EnergyCharge`는 0~4 화면 표시·시연 입력의 변환 경로로 유지했다. 기존 흡수 시연의 회복 비율을 실제 용량에 변환하며 새로운 고정 회복량은 임의로 정하지 않았다.
- 근거·의도: 본편에서 UI나 창 없이 실제 양·소비·회복·유예 계산을 재사용하고, 기존 HUD·CPU/GPU 흡수 경로의 시연 동작을 유지하기 위한 구현 선택이다. 구현 판단 시각은 위 기록 시각이며 사용자 발언 시각과 구분한다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- U3의 용량은 사용자가 직접 지정했다. A1의 구체적인 클래스 구조·코드나 실제 화면 결과를 사용자가 승인한 것으로 확대하지 않는다.

## 5. 반영 후 발견한 문제

- 작업 전 코드에는 자연 감소가 없었으며 `EnergyCharge`의 표시 값만 있었다. 실제 단위와 표시 값을 구분하지 않고 초당 0.5를 적용하면 레벨 용량 지정과 맞지 않는다. U2로 구현 전에 이 해석을 바로잡았다.
- 일반 에너지가 감소한 뒤에도 별도 추가 충전을 표시 합계에 더하면 실제보다 일반 레벨이 높게 계산될 수 있어, 일반 에너지가 완충됐을 때만 추가 표시 구간을 합산하도록 분리했다. 추가 충전 값 자체는 보존한다.
- 관련 자동 검사에서는 새 실패를 확인하지 않았다. 시각적 감소 속도·전투 사용감은 미검증이다.

## 6. 사용자 해결 제안과 실제 해결 과정

- U2·U3에 따라 실제 용량 100/200/400과 추가 200을 적용했다. 유예는 2초, 감소는 실제 양 0.5/초로 연결했다.
- 레벨별 실수량과 화면 비율을 변환하므로 같은 실제 소비량도 용량이 큰 레벨에서는 더 작은 비율 변화로 표시된다.

## 7. AI 해결 제안과 실제 해결 과정

- `EnergySettings`는 각 용량·유예 초·초당 감소량을 보관한다. `EnergyAmount`는 일반 에너지와 추가 충전을 나누고 실제 단위 회복·넘침·소비와 화면 변환을 계산한다. 레벨 하락은 기존 최대치−1 규칙을 적용하며 큰 시간 간격에서도 각 하락 경계를 처리한다. 일반 에너지는 0 아래로 내려가지 않는다.
- `EnergyDecay`는 유예를 넘긴 실제 시간만 소비량으로 반환한다. 일시정지·설정·메뉴에서 유예를 소모하지 않으며 Standby·Overdrive 중에도 자연 감소를 멈춘다. Standby 만료 시 유예를 초기화한다.
- `MovementApplication`은 이동 설정의 `energy`를 HUD에 주입한다. `HudPreview`는 CPU 입자 도착·GPU 도착 수신으로 실제 회복이 생기면 유예를 재시작한다. 입자 생성·자연 감소만으로는 재시작하지 않는다. UI의 표시 값을 실제 일반 에너지와 추가 충전으로 각각 변환한다.
- 기존 흡수 시연의 비율과 Overdrive의 실제 5초 유지·종료 후 LV1·0 동작은 유지한다. PRE-PRD의 에너지 소모 기반 Overdrive 설계를 구현 완료로 보고하지 않는다. 자동 가드의 실제 전투 연결도 이번 작업에 추가하지 않았다.
- 신규 `test_energy.py`의 10개 검사는 각 실제 용량·일반/추가 회복 넘침·추가 충전 보존·레벨 하락·시간 분할 독립·2초 경계·CPU/Compute 회복 후 유예 재시작·일시정지·Standby 만료·메뉴·Overdrive 시간 분리를 확인한다. Compute 경로는 도착 수신·갱신 요청 검사이며 실제 GPU 렌더링 확인이 아니다.
- `.venv-capability-test`에서 `test_ui_v2*.py` 140개를 실행해 137개 통과·선택 GPU 검사 3개 건너뜀을 확인했다. 별도로 에너지·Overdrive·무지개색·이동 HUD·검 이동/공격/효과·카메라 충격·레이더·피해 숫자 검사 148개가 모두 통과했다. 합계 **288개 중 285개 통과·3개 건너뜀·실패 0개**다.
- 실제 창 조작·장시간 감소/회복 재생·사용자 사용감 승인은 미수행이다. 관련 파일이 기존 작업과 함께 미추적·미커밋 상태라 관계없는 변경을 포함하는 커밋·업로드는 수행하지 않았다.

# 기본 콤보·실제 표시 크기·방향별 중심 정렬

- **기록 ID:** `FDLOG-20261112-combo-size-center`

- 개별 발언의 정확한 시각은 미확인이다. [[FDLOG_MISSING_TIME:FDLOG-20261112-combo-size-center:scope]] 현재 대화의 “기본 콤보 모션”, “검의 위치는 생성할 때 기록”, “실제 메카 크기”, “모든 방향에서 같은 플레이어 중심”과 보고를 검색한다.
- 상태: 별도 Unreal 콤보 후보·3시점 전체 프레임·검 좌표·Idle 크기/조립 정렬·OpenGL 확인. 사용자 동작 품질 승인·본편 공격 입력 연결·커밋·업로드는 별도다.

## 1. 사용자가 제안한 것

- **U1:** 현재 Idle KeyPose에서 기본 콤보로 자연스럽게 이어지고 마지막 타격 뒤 Idle로 돌아오게 한다. Trail 계산을 위해 생성할 때 검 위치를 기록한다. 연결감과 후속 Trail 계산이 직접 밝힌 이유다.
- **U2:** 여백을 포함한 표시 영역보다 실제 로봇이 차지하는 해상도를 기준으로 한다. 확인 질문에서 **손에 든 검을 포함한 전체 실루엣의 긴 변 256px**를 선택했다. 기존 768 원본 유지 조건은 보존한다.
- **U3:** 회전보다 공전처럼 보인다고 지적하고 파츠 조립에서 중심을 정렬하도록 요청했다. 모든 방향에서 같은 플레이어 중심에 놓는 것이 직접 지정한 기준이다.

## 2. AI가 제안한 것

- **A1, 구현상 판단:** 기존 4단 명세인 내려베기→가로베기→찌르기→뽑아베기를 타당 10프레임·12fps로 만든다. 준비·타격·회수·체중 이동을 읽을 수 있는 약 3.33초 초안이다. 원래 모델·리그·Idle은 보존한다.
- **A2, 구현상 판단:** 같은 손 로컬 파지를 모든 타에 유지하고, 저장된 AnimSequence에서 실제 검 변환을 120Hz로 다시 읽는다. 날 양끝은 기존 Unreal 검날 메시의 길이축 극값 정점 중심으로 추출한다. 게임 월드 값과 혼동하지 않도록 component cm·이미지 좌표를 구분한다.
- **A3, 구현상 판단:** 8방향 Idle 전체의 최대 실루엣을 같은 배율로 256px에 맞춘다. 각 프레임을 개별 확대하지 않고 콤보의 넓어지는 범위는 더 큰 캔버스로 확보한다.
- **A4, 구현상 판단:** 기존 카메라 높이 기준을 유지한 메카 중심 `[0,0,260]cm`를 모든 카메라에 투영해 조립 피봇을 정한다. 모든 파츠·마스크에 같은 방향별 피봇을 적용하고 최종 정수 출력 크기로 렌더 피봇을 계산한다. 자세별 bounding box 중앙을 따라가지 않는다.

## 3. 사용자 제안 중 AI가 수용한 것

- U1: 현재 Idle 0프레임에서 시작하고 마지막 구간을 Idle 10~12프레임으로 연결하는 4개 새 AnimSequence를 작성했다. 검 위치·회전·날 양끝·8방향 투영 좌표를 별도 JSON으로 보존했다.
- U2: 768 원본은 유지했다. 기존 256 표시 영역의 사선은 실제 약 59×103~106px였음을 확인했다. 최종 OpenGL 출력은 검 포함 최대 긴 변 256px, 중심 정렬 후 사선 9프레임은 130×222px다.
- U3: 방향별로 같은 메카 기준점을 플레이어 좌표에 정렬한 새 조립 에셋으로 UI를 다시 실행했다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- U2의 검 포함 256px·U3의 공통 중심은 사용자가 직접 선택/요청했다. 10프레임 타이밍·개별 자세·120Hz·내부 중심점 높이는 구현 판단이며 별도 사용자 품질 승인으로 해석하지 않는다. 크기/정렬 후속 피드백을 콤보 품질 승인으로 확대하지 않는다.

## 5. 반영 후 발견한 문제

- **I1:** 첫 콤보 후보의 준비·2→3타 연결에서 검 손이 어깨 가까이를 지나 팔 굽힘이 약 131~134도까지 커졌다. AI가 저장된 포즈의 각도와 전체 사선 프레임을 확인해 발견했다. 좁은 V자 접힘을 검토 통과로 남기지 않았다.
- **I2:** 256×256 캔버스 기준은 실제 로봇 크기와 달랐다. 사용자가 여백을 지적해 실루엣 기준으로 바꿨다.
- **I3:** 렌더 카메라는 `[50,0,260]cm`를 바라보는데 조립 피봇을 전 방향 `[384,384]`로 고정했다. 메카 기준점의 투영이 방향에 따라 달라져 표시 배율에서 좌우 약 39.4px의 이동이 생겼다. 작은 비정수 확대에서는 출력 사각형의 크기/원점을 따로 버림 처리하는 오차도 있었다.
- **I4:** 실제 호스트의 GeometryScript 리스트 변환·Transform 회전 인자 형식이 첫 구현과 달라 진단 실행이 실패했다. 구조체의 변환 메서드와 Transform 속성 할당으로 고쳤고 기존 동작을 덮어쓰지 않았다.

## 6. 사용자 해결 제안과 실제 해결 과정

- I2 ↔ U2: 긴 변 기준을 실제 검 포함 실루엣으로 변경했다. Idle 96장의 원본 최대 긴 변은 355px다. 고정 배율 0.7183098591549296과 bicubic·알파>0 기준의 실제 OpenGL 측정으로 최종 최대 256px를 확인했다.
- I3 ↔ U3: 파츠 조립 manifest에 방향별 `clips[].pivot`을 넣었다. 새 `player_mech_idle_centered_8dir/mech.json`을 만들고 UI에 연결했다. 16개 색상/마스크 PNG의 해시는 이전 패킹 결과와 같으며 변경은 피봇 메타데이터와 렌더 사각형 계산이다.

## 7. AI 해결 제안과 실제 해결 과정

- I1 ↔ A1: 손 경로를 몸 앞의 큰 호로 바꾸고 몸통 회전을 줄인 v2 후보를 작성했다. 검 팔 굽힘 범위는 1타 약 49.92~109.88도, 2타 74.22~97.70도, 3타 28.95~88.35도, 4타 28.95~55.73도다. 이는 초안 검사값이며 프로젝트 공통 관절 제한을 확정한 것이 아니다.
- `automate/unreal/pose_math.py`·`pose_targets.py`를 공통화하고 `unreal-plan` 경로를 추가했다. 회전으로 두 관절 목표를 풀며 본 길이를 바꾸지 않는다. 도달 범위를 벗어난 목표는 출력 전에 거절한다. 직접 작성한 막대 수치 샘플을 `samples/unreal_pipeline/pose_targets/`에서 독립 실행했다.
- 저장 후보는 `/Game/MechLab/SwordCombo_20261111_v2/01~04/A_Combo01~04`다. 원래 사용자 프로젝트에 새 동작 4개·검토 장면 파일 84개를 복사하고 해시를 확인했다. 별도 프로세스에서 재로딩한 본 위치는 생성 결과와 같고, 시작 Idle 위치 오차 0cm·끝 Idle 위치 오차 약 0.0000038cm·타 사이 최대 위치 오차 약 0.0000018cm·파지 오차 약 0.000104cm다. 기존 Idle 해시는 유지됐다.
- A2: `blade_tracking.py`가 검 본 위치·xyzw 회전·실제 날 양끝·8카메라 좌표를 기록한다. 각 타의 101표본은 원래 사용자 프로젝트 재로딩 후에도 정확히 같았다. 경계 중복을 제외한 401표본을 `data/animations/player_mech/basic_combo_20261112/blade_trajectory.json`에 보존했다. 조립 중심 보정 후 방향별 top-left 피봇과 화면 좌표 계산식도 갱신했다. 120Hz 재평가는 저속 원본 키 사이의 평가 결과이며 새로운 모션 정보가 추가됐다는 뜻은 아니다.
- 정면·측면·사선 120프레임의 8파츠·Energy Mask·통합 참조를 출력했다. 모든 프레임의 조립 실루엣은 통합 참조와 같고 960개 마스크의 알파도 소유 파츠와 같다. RGB 차이 2를 넘는 검 경계 픽셀은 전체 10개였다. 전체 프레임 시트와 확대·좌표 오버레이를 직접 열어 확인했다. 정면 찌르기의 단축 투영은 측면/사선과 함께 검토했다.

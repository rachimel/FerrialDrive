# 플레이어 파츠·잔상 키포즈 유니폼 재사용

- **기록 ID** `FDLOG-20261122-player-part-paint`
- 2026-11-22 KST 계측. RTX 5070 Laptop, FHD·Medium·SMAA, 적 180기·15m 간격, 플레이어 HP 10만, 고정 60Hz 자동 검 입력, 무음, VSync와 프레임 제한 해제.

## 1. 사용자가 제안한 것

- **U1** `PicoPartMotion.draw` 안의 `PartPainter.paint`를 더 나눠 계측하고 플레이어 파츠와 잔상을 최적화한다. 같은 180기 입력과 품질에서 화면을 유지하고 전후 함수 시간과 FPS를 별도 커밋으로 남긴다. 정확한 요청 시각은 미확인이다. `[[FDLOG_MISSING_TIME:FDLOG-20261122-player-part-paint:U1]]`. 검색 단서는 `다음은 플레이어 파츠·잔상 쪽 최적화`다.

## 2. 사용자 제안 중 AI가 수용한 것

- **U1** 깊이·본체·반해상도 잔상을 구분했다. `paint` 안에서는 포즈 배열 준비, 배열과 스칼라 유니폼 제출, 배치와 텍스처·그림자 바인딩, 사각형 제출을 나눴다. 동일 배경에 그린 전후 RGBA와 교전 상태를 확인했다.

## 3. AI가 제안한 것

- **A1 · 구현상 판단** 2026-11-22 KST 초기 계측에서 전후 개선 후보를 고르기 위해 실제 제출의 동일 포즈 배열을 세었다. 916회 중 804회에서 앞서 본 배열 키가 반복됐다. 비페이지 PBR의 셰이더별 최근 키포즈 유니폼을 64개까지 보관하고, 현재 프로그램에 같은 배열이 있으면 재전송을 건너뛰기로 했다.
- 방향 리소스의 적재본 식별자·키포즈 쌍·재투영 뱅크 배치로 타일 배열을 구분한다. 매 패스에서 시간 위상, 허리 정렬·상하체 위치 보정, 각도 행렬, 색·밝기·투명도·조명 유니폼을 기존 시점에 올린다. 페이지 풀이 타일 좌표를 바꿀 수 있는 경로와 인스턴스 포즈 테이블은 기존 배열 처리 경로를 사용한다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- 화면 유지와 전후 비교는 사용자 요청이다. 캐시 크기, 교차 실행 순서, 화면 비교 단위는 구현상 판단이다.

## 5. 반영 후 발견한 문제

- **I1** 단일 계측의 `PartPainter.paint`는 프레임당 평균 4.11ms였다. 그중 배열 준비 0.58ms, 배열 유니폼 제출 0.86ms, 아틀라스 바인딩·복원 0.80ms였다. 0.86ms 구간은 배열용 `PartPainter.upload` 경과와 중첩된다. 초기 시간은 개선 대상 선택에 사용했다.
- **I2** 전후 별도 실행의 입력·교전 상태 120개는 모두 일치했다. 아틀라스 백그라운드 준비 시점이 개별 제출 수에 영향을 줄 수 있다. 상세 계측의 파츠 제출은 평균 7.73 → 7.69회/프레임이었다. 픽셀 비교에서는 한 실행의 동일 호출 인자를 전후에 전달했다.

## 6. 사용자 해결 제안과 실제 해결 과정

- **U1** 30프레임 예열과 120프레임 측정을 전후 각각 4회 교차 실행했다. 비교 기준은 `e07ea3e`와 기존 로컬 변경이 포함된 작업본이다. 전후 사이에는 파츠 캐시 구현만 교체했다.
- 계측 없는 FPS 중앙값은 **32.63 → 33.54**(+2.8%)였다. 회차별 FPS는 전 32.23·34.32·31.62·33.02, 후 34.41·33.54·33.54·33.31이다. 회차별 프레임 작업 P50의 중앙값은 29.07→29.18ms, P95는 40.26→39.01ms, P99는 48.07→43.10ms였다.
- 같은 실제 OpenGL 대상에서 배경을 바이트 단위로 복원하고 독립 셰이더 두 개로 비교했다. 120프레임에서 색상 269회·깊이 120회·잔상 561회, 총 950회·10,776,326픽셀에 차이가 없었다. 그중 방향 재투영 제출이 324회였다. 비교한 같은 호출 집합에서 배열 제출 `glUniform4fv`는 16,704→11,233회(−32.8%)였다.

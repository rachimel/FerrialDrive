# HUD 배치 렌더링 큐와 구조체 재사용

- **기록 ID:** `FDLOG-20261115-hud-batch-render-queue`
- 작성·확인 범위: 2026-11-15 현재 대화와 현행 코드. 사용자 요청의 개별 시각은 미확인: `[[FDLOG_MISSING_TIME:FDLOG-20261115-hud-batch-render-queue:scope]]`. 검색 단서: `HUD의 요소들을 Batch Rendering Queue`, `구조체 재사용은 어떤게 가능해`.
- 실제 OpenGL 비교 시작: 2026-11-15 14:50:20 KST. 공격 상태 픽셀 대조 시작: 14:53:24 KST. 문서 정리 확인: 14:55 KST 이후. 원문 요청 시각과 구분한다.
- **상태:** 큐 연결·버퍼 재사용·자동 검사·숨김 실제 GL 실행·HUD 단독 픽셀 확인 완료. 최소 사양 FPS 달성·수백 기 전투·장시간 조작·사용자 외관 승인·커밋·업로드와 구분한다.

## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1):** HUD 요소를 Batch Rendering Queue에 넣어 묶어서 실행한다. 앞선 ctypes 반복 호출 비용 조사에 이어 실제 HUD 제출을 개선하는 요청이다. 제안 시각·출처는 scope를 따른다.
- **사용자 제안 2 (U2):** 구조체 재사용이 가능한 대상을 확인한다. 제안 시각·출처는 scope를 따른다.

## 2. 사용자 제안 중 AI가 수용한 것

- U1: Pico2D·SDL 모듈 원본을 유지하고 `HudBatchQueue`를 메뉴·일시정지·전투 HUD에 연결했다. 같은 텍스처·상태의 연속 도형만 합친다. 입력 순서·투명도·클리핑·배율·렌더 대상·블러 순서를 유지한다.
- U2: 큐에 필요한 SDL_Vertex 배열과 position/color/UV view, 정수 인덱스 배열, SDL_Rect 배열을 렌더러별로 재사용한다. 중첩 상태 저장용 viewport/clip 구조체는 단일 객체로 공유하지 않는다.

## 3. AI가 제안한 것

- **AI 제안 1 (A1), 구현상 판단:** 텍스처 전역 정렬 대신 연속 구간을 묶고 상태 변경·즉시 그리기를 제출 경계로 삼는다. 반투명 도형의 겹침과 레이어 순서가 달라지는 것을 막기 위해서다. 현재 대화의 구현 전 진행 보고와 큐 코드가 근거다.
- **AI 제안 2 (A2), 구현상 판단:** 1:1 배율의 링 span을 사각형 배열로 제출한다. 다른 배율은 기존 선 처리를 유지해 확대·축소 시 픽셀 의미가 바뀌는 것을 피한다.
- **AI 제안 3 (A3), 검증 판단:** 같은 장면·설정에서 큐 켜기/끄기 순서를 뒤집어 비교하고, 픽셀은 정지/공격 장면의 반복 대조와 HUD 단독 대조를 나눈다. 실행 순서·캐시와 기존 월드 재그리기의 차이를 큐 회귀로 잘못 판단하지 않기 위해서다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- U1은 구현 명시 요청이다. A1~A3의 세부 API·용량·1:1 배율 경계·시험 조건을 별도로 확정한 사용자 규격으로 확대하지 않는다. 구조체 재사용은 큐 내부의 필요한 버퍼에 적용했으며 모든 임시 구조체를 제거한 것으로 보고하지 않는다.
- 화면 캡처·자동 픽셀 동일성은 사용자의 직접 조작이나 최종 외관 승인이 아니다.

## 5. 반영 후 발견한 문제

- **I1, AI 발견:** 첫 스캔라인 삼각형 fan 병합에서 기존 배율별 전역 띠 정렬 검사가 실패했다. SDL software가 공유 인덱스 삼각형 두 개를 사각형 복사로 재해석하는 경로가 원인이었다. 해당 초기 결과는 최종 통과 근거에서 제외한다.
- **I2, AI 발견:** 첫 전투 화면 두 장의 픽셀이 달랐다. 추가 공격 상태 대조에서 큐를 끈 연속 재그리기에도 차이가 발생했고, 차이는 화면 가장자리 8px 안에만 있었다. HUD 단독 대조는 완전히 같았다. 기존 월드/카메라 블러의 재그리기 누적과 분리하며 이번에 월드 표현은 수정하지 않았다.
- **I3, AI 발견:** 초기 진단 보고서의 큐 비활성 조건이 직전 활성 배치 통계를 보관할 수 있었다. 활성 여부와 비활성 시 null을 명시하도록 보고 메타데이터를 보정했다. 첫 비교의 비활성 `hud_batch_last`는 분석 근거에서 제외하며 실제 SDL 호출 계수와 프레임 기록은 유지한다.

## 6. 사용자 해결 제안과 실제 해결 과정

- U1: HUD 호출은 순서대로 큐에 쌓고 동일 상태의 구간을 `SDL_RenderGeometry` 또는 `SDL_RenderFillRects`로 실행한다. 텍스트/이미지 복사·즉시 선·클리핑·배율·viewport·렌더 대상·GL 전환 전에 제출한다. 전체 HUD를 하나의 GPU draw call로 합친다는 뜻이 아니다.
- U2: 정점과 하위 구조체 view, 인덱스, 링 사각형 배열을 다음 프레임에도 유지한다. 충분히 예열한 실제 장면의 마지막 배치에서 버퍼 신규 할당은 0회였다. 변경한 값만 CPU 배열에 쓰며 GPU 업로드·네이티브 호출 비용 자체가 없어지는 것은 아니다.

## 7. AI 해결 제안과 실제 해결 과정

- I1 ↔ A1: 스캔라인·노이즈는 각 삼각형의 인덱스를 분리해 software의 사각형 재해석을 막았다. 묶음 제출과 UV·배율별 삼각형 처리 의미를 함께 유지한다. 기존 UI v2 검사 137개 중 134개 통과·GPU 선택 3개 생략이다.
- A1/A2: 새 큐 검사 13개 통과. 실제 Windows/OpenGL 4개와 SDL software 4개, 버퍼·순서·실패 정리 5개를 포함한다. 연속 삼각형 12회 요청은 1회 제출, 링은 1회 사각형 제출을 확인했다. 실패 시 clip·scale·viewport·렌더 대상 복원과 명령 재실행 방지도 확인했다.
- 영향 범위 검사: 큐 포함 63개 실행에서 진단기의 게임 없는 보고 호환 1건을 고친 뒤 해당 진단기 4개를 재확인했다. 나머지 UI core·장비·피해·아이콘·훈련장 연결 검사는 통과했다. 중복 실행을 합쳐 고유 검사 수로 보고하지 않는다.
- A3: 실제 RTX 5070 Laptop·Python 3.11.16·FHD·저장 품질 low·자원 제한 없음·숨김 창에서 고정 1/60초 갱신, 준비 120/측정 360프레임으로 큐 켜기/끄기를 각각 2회 실행했다. 두 번째 회차는 역순이며 FPS 제한·VSync는 껐다. 일반 구간 타이머만 쓰고 상세 호출 계수는 별도 120프레임에서 수집했다.
- 전체 work 평균은 큐 끔 16.80ms, 큐 켬 14.29ms로 약 15% 감소했다. HUD 포함 wall 평균은 8.37→5.78ms로 약 31% 감소했다. 켠 조건의 work p95는 26.40/26.45ms이고 360프레임 중 92/94프레임이 60FPS 예산을 초과했다. 평균 개선을 최소 사양 60FPS 보장이나 권장 165FPS 달성으로 해석하지 않는다.
- 별도 상세 계수에서 HUD의 프레임당 SDL_RenderGeometry는 약 229.8→45.9회, SDL_RenderDrawLine은 약 659.4→11.4회였다. 링 648개 span을 포함한 사각형은 평균 약 2.3회의 SDL_RenderFillRects로 처리됐다. 이 값은 GPU draw call의 직접 측정값이 아니다.
- I2 ↔ A3: 정지 장면의 전체 화면 켜기/끄기·동일 조건 반복은 픽셀이 같았다. 공격 장면의 HUD 단독 픽셀도 완전히 같았으며, 전체 화면의 반복 차이는 가장자리 8px 안에만 있었다. 저장한 전체 장면·HUD 단독·차이 이미지를 직접 열어 확인했다.
- 원자료: `output/performance/hud_batch_20261115/145020_434296/`의 비교·상세 계수·원본 캡처, `145258_607116/`의 정지 장면 대조, `145324_683826/`의 공격 장면 대조. 소스 SHA-256·설정 스냅샷을 결과에 포함한다. 저사양 실기 환산은 하지 않는다.
- 현재 사용법과 큐의 경계는 `docs/unit-tests/ui_unit_test.md`, 진단용 `no_hud_batch`는 벤치마크 사용법에 반영했다. 기존 대량 미커밋 변경과 관련 파일이 겹치므로 커밋·업로드는 하지 않았다.

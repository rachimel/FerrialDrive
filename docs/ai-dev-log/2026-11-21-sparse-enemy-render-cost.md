# 적 보간·인스턴싱 제출 비용

**기록 ID** `FDLOG-20261121-sparse-enemy-render-cost`

**작성 시각** 2026-11-21 15:51 KST. 실제 게임용 Python과 Intel iGPU를 사용했다.

## 1. 사용자가 제안한 것

- **U1** 34→28 FPS 결과의 원인을 조사하고 적 보간과 인스턴싱의 비용을 따로 재서 60 FPS 우선순위를 제시한다.
- **U2** 같은 텍스처를 읽는 적을 한 번에 제출할 수 있는지 검토한다.
- 정확한 발언 시각은 [[FDLOG_MISSING_TIME:FDLOG-20261121-sparse-enemy-render-cost:U1-U2]]이다. 같은 대화에서 `적 중간 프레임 보간이랑 인스턴싱 비용 따로 재보고`, `같은 텍스쳐 공유하는 놈들끼리`로 찾을 수 있다.

## 2. 사용자 제안 중 AI가 수용한 것

- **U1** 같은 28기 자동 입력에서 보간 위상, 근거리 합성 시트, 원거리 캐시 복사를 각각 바꿨다. 24기 본체만 그리는 시험으로 CPU 제출과 OpenGL 타이머 결과를 대조했다.
- **U2** 같은 합성 시트에서 서로 다른 영역을 읽는 12·24·64개 복사를 기존 앞뒤 순서 그대로 묶어 픽셀과 비용을 비교했다.

## 3. AI가 제안한 것

- **A1** 확대 진입 시 개별 렌더로 빠지는 적을 시트 합성에 포함하는 방안을 먼저 검토한다. 기존 확대 품질을 유지하는 시트 확대가 후보이며 실장면의 FBO 전환 수와 화질로 검증해야 한다.
- **A2** 적 확대 경로 다음으로 HUD와 플레이어 PBR 제출을 검토한다. 16.67ms 목표와 비교할 때 CPU 작업 시간이 가장 크게 초과했다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- 제안은 이번 진단의 결론이며 적용 결정은 후속 검토 사항이다.

## 5. 반영 후 발견한 문제

- **I1** 최초 고품질 FHD 28기 결과의 프레임 작업은 29.28→35.19ms였다. 재검사 두 번에서는 기존 27.1~30.6 FPS, 새 방식 35.9~41.8 FPS로 순서가 바뀌었다. 첫 수치만으로 지속적인 총 FPS 하락을 단정할 수 없다.
- **I2** 기존→새 방식의 적 본체 GPU 합성 수는 프레임당 11.1→22.4개, 적 렌더의 SDL 타깃 전환은 2.4~2.8→32.3~32.6회였다. 한 기만 쓰는 원거리 위상은 프레임마다 다시 그린다. 확대 조건에서는 묶음 합성을 건너뛰고 개별 Bicubic·SMAA 경로를 탄다. 이 경로의 타깃 전환만 29.6회였다.

## 6. 사용자 해결 제안과 실제 해결 과정

- **U2** 서로 다른 포즈를 같은 시트에서 읽어 묶을 수 있었다. 24개 복사 테스트에서 개별 복사, SDL 기하 제출, OpenGL 인스턴싱의 픽셀이 일치했다. CPU 제출 시간은 각각 0.027ms, 0.057ms, 0.061ms였다. 조건당 100프레임의 평균을 구해 3회 중앙값을 사용했다.

## 7. AI 해결 제안과 실제 해결 과정

- **I2 ↔ A1** 시험에서 적 확대만 끄면 타깃 전환은 4.65회까지 줄었으나 전체 프레임 시간의 개선 폭은 두 회차에서 일관되지 않았다. 24기 독립 시험에서 기존 근거리 시트 합성은 개별 렌더보다 CPU 제출이 4.64→1.59ms로 줄었다. 같은 시트에서 보간의 GPU 비용은 키포즈 0.89ms, 보간 1.94ms였다.
- **I2 ↔ A1** 이미 합성한 같은 포즈 4기 복사는 SDL 0.014ms, GL 인스턴싱 0.081ms였다. 128기에서는 0.178→0.118ms였다. 28기 장면에서 원거리 인스턴싱은 본체와 그림자를 합쳐 0.27회/프레임이었다.
- **A2** 현재 28기 재검사의 전체 CPU 작업은 26.36~32.83ms, GPU 전체 draw 시간은 9.66~11.22ms였다. 같은 교전의 HUD 제출 포함 시간은 6.94~9.28ms였고, 별도 상세 계측에서 플레이어 표면은 4.51~5.65ms였다. CPU 포함 시간과 GPU 시간을 더해 프레임 비용으로 사용하지 않는다.

## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1):** `TimingRecorder`를 기억하기 쉬운 이름으로 부른다. 이유: 사용자가 이름을 기억하기 어렵다고 직접 설명했다. 시각은 scope 누락 참조, 출처는 `TimingRecorder는 좀 기억하기 그러니까` 발언이다.
- **사용자 제안 2 (U2):** CPU·GPU 사용률, 호출 스택을 기록하고 기록 비용을 재서 차감하는 방향을 검토한다. 호출 스택 활용은 Flame Graph로 정정했다. 이유: 사용자와 AI가 성능 문제의 원인을 찾는 데 현재 집계 도구가 부족하다고 판단했다. 시각은 scope 참조, 출처는 `현재 FDrive Profiler로는 부족할건데` 발언이다.
- **사용자 제안 3 (U3):** 기존 profile 계열 도구를 게임에 간단히 연결한다. 이유·근거는 U2와 같다. 시각은 scope 참조, 출처는 `그냥 profile을 대충 우리게임이랑 연결하는걸로 할까` 발언이다.

## 2. 사용자 제안 중 AI가 수용한 것

- U1·U3 수용. 명칭은 성능 프로파일러(FDrive Profiler), 실제 스택 수집은 검증된 외부 수집기를 연결하는 방향으로 정리했다.
- U2의 사용률·스택 수집 목적은 수용했다. 비용 차감은 실행 교란을 모두 복구하지 못하므로 정확도 보장이 아닌 추정 보정으로 한정하자고 제안했다. 이번 단계에서는 사용률과 보정을 구현하지 않았다. 제안·수용 시각은 scope 참조.

## 3. AI가 제안한 것

- **AI 제안 1 (A1):** Flame Graph 중심이므로 `py-spy`를 수집기로 사용하고 FDrive Profiler는 연결·수집·분석 진입점을 담당한다. 사용자용 Flame Graph와 AI용 구조화 로그를 같은 실행에서 만든다. 이유: 현재 `TimingRecorder`에는 이름별 시간 합계만 있고 전체 호출 경로가 없다. 시각은 scope 참조. 근거: 현재 코드와 [py-spy](https://github.com/benfred/py-spy).
- **AI 제안 2 (A2):** 스택 수집을 먼저 검증하고 CPU/GPU 사용률과 자체 시간 보정은 후속으로 둔다. 원본을 보존한다. 이유: 최소 연결로 실제 병목 후보를 찾는 데 도움이 되는지 확인하기 위해서다. 시각은 scope 참조.
- **구현상 판단:** py-spy 0.4.3, 기본 100Hz·30초, Speedscope JSON 원본과 별도 AI 요약, 새 폴더만 생성, PID 연결/파일 실행 두 경로를 선택했다. 이 세부 값과 CLI 구성을 사용자의 개별 승인으로 기록하지 않는다.

## 5. 반영 후 발견한 문제

- **문제 1 (I1):** Windows 가상환경의 `python.exe` 실행에서 py-spy가 Python 버전을 찾지 못했다. AI가 독립 시연 중 발견했으며 권한 밖 재시도에서도 같은 결과였다. 직접 시작한 가상환경 중개 프로세스와 실제 Python 자식의 차이가 원인이었고 자식 수집 후 정상 스택이 기록됐다. 최초 발견 시각은 수집 로그 기준 2026-11-11 18:11:03 KST다.
- **문제 2 (I2):** 설치 및 기존 타이머 검사에서 실행 환경의 임시 폴더 접근 제한이 발생했다. 기능 오류로 확정하지 않았다. 허용된 재실행에서 설치와 기존 7개 검사가 통과했다.

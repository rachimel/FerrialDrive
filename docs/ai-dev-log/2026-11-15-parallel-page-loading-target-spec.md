# 페이지 Work 병렬 적재·반해상도 그림자·성능 목표

- **기록 ID:** `FDLOG-20261115-parallel-page-loading-target-spec`
- 대화·기록 날짜: 2026-11-15 KST. 개별 발언 시각은 미수집이다. `[[FDLOG_MISSING_TIME:FDLOG-20261115-parallel-page-loading-target-spec:scope]]` 검색 단서: `독립적인 Work`, `Page Table Virtual Texture`, `반해상도로`, `1GB 내외`, `그림자는 원래 부드럽게`.
- 근거: 현재 대화·사용자 첨부 그림자 화면, 현행 소스, `output/performance/loading_20261114/`의 JSON·전후 캡처. 폴더 날짜는 이전 조사 경로를 재사용한 것이며 발언 날짜가 아니다.
- **상태:** 병렬 적재·50% 기본 품질·반해상도 R8 그림자·부드러운 표시 구현. 상주 예산 관리·Page Table VT·추가 축소·대규모 전투·고주사율 출력 구현은 이번 범위 밖이다. 사용자 직접 조작·최종 외관 승인·커밋·업로드 없음.

## 1. 사용자가 제안한 것

- **U1:** lock으로 동기화하는 병렬 압축 해제와 페이지별 독립 Work를 요청했다. 의도는 앞선 압축 해제 병목을 줄이는 것이다. 출처·시각은 scope 참조.
- **U2:** 액션 증가를 고려한 Page Table VT 검토와 현재 보간 데이터 수량을 질문했다. 출처·시각은 scope 참조.
- **U3:** 50% 보간 품질이 모션 블러와 함께 큰 차이가 나지 않았다고 관찰했다. 보간 데이터와 현재 설정을 50%로 하고 추가 다운샘플링도 고려하자고 했다. 현재 확인한 장면의 피드백이며 모든 동작 승인으로 확대하지 않는다. 출처·시각은 scope 참조.
- **U4:** KTX2·Oodle의 관계와 zlib-ng/zlib-rs 사용 여부를 질문했다. 답변 근거는 현행 코덱·프로필과 실제 Python 환경이다. 출처·시각은 scope 참조.
- **U5:** 현재 사용량과 미래 목표로 모니터 주사율별 사양표를 만들고 부품별 선택 이유를 요청했다. 후속 확인으로 FHD·QHD, 소수 기종의 에셋을 공유하는 수백 기 규모를 지정했다. 출처·시각은 scope 참조.
- **U6:** 전체 메모리 목표를 검토한 뒤 최종적으로 기본 시나리오 1GB 안팎, 시나리오 규모가 커지면 2GB로 높이는 방향을 지정했다. 문서 단위는 기존 표기에 맞춰 GiB로 정리했다. 중간의 수백 MB 검토를 최종 결정으로 기록하지 않는다. 출처·시각은 scope 참조.
- **U7:** 첨부 화면의 그림자 윤곽이 지나치게 날카롭다고 지적하고 부드러운 표현을 요구했다. 반해상도 대상이 그림자임을 후속 확인으로 명시했다. 원본 PNG 수정이나 실제 3D 광원 재제작 요청으로 확대하지 않는다. 출처·시각은 scope 참조.

## 2. 사용자 제안 중 AI가 수용한 것

- U1: 페이지별 CPU 준비와 GPU 소비를 분리하고 4개 이내 병렬 Work를 연결했다. lock은 상태·결과 교환에만 사용했다.
- U3: 기본값과 현재 저장 설정을 `low` 50%로 맞췄다. 준비된 프로필을 한 번 선택하며 중복 축소하지 않는다.
- U5·U6: [성능 목표 검토](../performance_targets.md)에 실측·잠정 장비·선택 이유·미검증을 구분했다. PRE-PRD는 기본 1GiB·큰 시나리오 2GiB와 미확정 항목만 반영했다. 기존 Iris·RAM 8GB 목표를 외장 GPU 최소 사양으로 임의 교체하지 않았다.
- U7: 원본·프레임·피봇을 보존하고 50% R8 제작 데이터를 준비했다. 부드러운 가장자리는 기존 GPU 그림자 보간 경로에서 표시했다. 수용·조치의 출처는 현재 대화와 변경 소스이며 개별 시각은 scope 참조.

## 3. AI가 제안한 것

- **A1:** `TexturePageWork`가 읽기·해시·해제를 소유하고, Future가 완료/예외 대기, Lock이 단일 결과 소비를 담당한다. 진행·완료 대기 Work를 합쳐 최대 4개로 제한한다. 이유는 CPU 해제를 겹치면서 메모리 폭증·GPU 컨텍스트 경쟁을 피하기 위해서다.
- **A2:** 현재/다음 모션의 필요 페이지 요청·상주 예산 관리를 우선 검토한다. 약 19MiB를 참조하는 단일 클립에 비해 전체 보간은 236MiB이고, 액션 증가와 1GiB 목표가 있어 검토 근거가 충분하다. 타일 단위 VT의 간접 조회·필터 경계·페이지 교체 비용은 별도 검증 대상으로 제안했다.
- **A3:** 사양표의 구체적인 CPU/GPU 모델과 1GiB의 항목별 배분 수치는 AI의 검증 후보·예산 검토안이다. 실제 최소 사양이나 사용자가 고른 부품으로 취급하지 않는다. 제조사 명세는 기능·용량 근거이며 게임 FPS 증거가 아니다.
- **A4:** 50% 그림자의 원본 논리 크기와 실제 텍스처 크기를 분리하고, 화면 5px 반경의 5×5 가중 필터를 적용한다. 접지 원점 가까이는 번짐을 줄인다. 이는 AI의 구현상 판단이며 정확한 3D 높이·광원 기반 반그림자 계산은 아니다.
- 제안 근거는 현행 소스·이번 실측·첨부 화면이며 개별 시각은 scope 참조.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- 병렬·독립 Work·lock은 U1로 요청받았다. 50% 보간/설정·50% 그림자·부드러운 표현·메모리 목표는 U3·U6·U7로 명시 요청받았다.
- A2의 페이지 상주 관리·Page Table VT 구현, A3의 부품명·세부 예산, A4의 정확한 5px/56px 수치는 사용자 별도 승인 전이다. 구현 보고나 침묵을 외관 최종 승인으로 취급하지 않는다.

## 5. 반영 후 발견한 문제

- **I1:** 액션 확장 시 전체 모션 사전 적재는 기본 1GiB 목표와 충돌할 수 있다. 기존 2GiB 기준·모든 기종의 전 모션 적재를 유지하는 것으로 해석하지 않는다.
- **I2:** 현 장비의 1기 공격에서도 CPU 측 프레임 경과가 60Hz 예산을 초과했다. 수백 기·Iris·고주사율 성능은 미검증이다. 로딩 병렬화와 텍스처 메모리 절감을 전투 FPS 해결로 보고하지 않는다.
- **I3:** 그림자의 날카로운 윤곽은 원본 알파에 이미 있었다. 초기 알파 전용 전환의 전후 픽셀이 같았다는 근거가 있어 이번 전환이 새로 날카롭게 만든 것으로 단정하지 않는다.
- 최초 실제 그림자 비교는 진단 래퍼가 새 `expected_size` 인자를 받지 못해 중단됐다. 진단 연결부를 수정하고 실패 폴더를 보존한 별도 이름으로 다시 실행했다. 제품 로더 오류로 집계하지 않는다.

## 6. 사용자 해결 제안과 실제 해결 과정

- I1 ↔ U1·U3: 독립 페이지 Work·제한된 병렬 대기열을 연결하고 기본 품질을 50%로 정했다. zlib-ng·zlib-rs·다른 압축 라이브러리는 도입하지 않았다. 실제 사용 환경은 Python 기본 zlib 및 conda `libzlib` 1.3.2다.
- U4: 현재 모든 게임 품질 프로필은 Oodle로 제작한 BC7 색상의 zlib 파일과 무손실 RGBA 벡터의 zlib 파일을 쓴다. KTX2/UASTC는 비교 후보·호환 코드이며 현재 게임의 선택 경로는 아니다. KTX2 컨테이너와 Oodle 인코더의 역할을 구분해 설명했다.
- I1 ↔ U6: PRE-PRD의 기본 전체 목표를 1GiB로, 큰 시나리오는 2GiB로 정리했다. 항목별 배분은 미구현 검토안이며 RAM/VRAM 중복 계측 기준도 후속 확인이 필요하다.
- I3 ↔ U7: 그림자 18장을 50% BOX 필터로 준비했다. 픽셀 합계는 281,158,320→70,298,568, R8 페이로드는 268.13→67.04MiB다. 원본 PNG 해시·프레임 좌표·피봇을 유지하고 실제 적재 크기로 자원량을 계산한다.

## 7. AI 해결 제안과 실제 해결 과정

- I1 ↔ A1: `texture_page_work.py`는 SDL·OpenGL을 import/호출하지 않는다. 각 Work는 해제 상태·KTX 변환 객체도 독립 소유한다. GPU 캐시는 소유 스레드를 검사하고 요청 순서·기존 공유/참조 수를 유지한다. 오류/취소 시 대기 작업을 취소하고 실행 작업 종료 후 이미 만든 GPU 자원을 렌더 스레드에서 정리한다.
- 관련 CPU·실제 OpenGL 검사 41개가 통과했다. 별도 검 이동 연결 검사 31개도 보간 OFF에서 부드러운 그림자 경로를 유지하는 동작을 반영해 통과했다. 합계 72개이며 전체 프로젝트 검사 통과나 이전 별도 잔상 검사의 해결로 확대하지 않는다.
- 4 Work와 1 Work의 50% 보간 화면 캡처는 그림자 축소 전 바이트가 동일했다. 해제 완료 대기·원본/축소 텍스처의 좌표·부드러운 가장자리·인접 프레임 번짐 방지·기존 교차 시트 피봇을 실제 GPU에서 확인했다.
- 병렬 비교는 같은 설정 해시 `4e03632c0eeb178f22db9ea8c39e95af5e7a900412120204d945b4c72ed097a0`을 사용했다. 보간 100%는 첫 화면 1 Work 3.87초/4 Work 2.68초, 50%는 1 Work 2.10~2.63초/4 Work 1.84초였다. OS 캐시·계측 비용은 통제하지 않았으며 CPU Work별 경과 합은 서로 겹친다.
- 그림자 전후 비교는 별도 동일 설정 해시 `cade607f59815ba7cb02fe94ce4775b25e0b45f96ced3aca048a770acf2be437`을 사용했다. 50% 보간/4 Work에서 원해상도·날카로운 그림자 1.73초, 50%·날카로운 그림자 1.62초, 50%·부드러운 그림자 1.66초였다. 원본·50%·50%+번짐을 나눠 캡처하고 직접 확인했다. 각 1회이며 Python 프로세스 생성은 제외한다.
- 후속 확대 캡처 `shadow_preview_hard/mech.png`·`shadow_preview_soft/mech.png`를 같은 설정으로 저장해 직접 비교했다. 두 실행 모두 18장 전체를 원본 알파의 BOX 축소 기준과 대조해 일치했다. 부드러운 조건의 후속 첫 화면은 약 1.58초였다. 검증용 PNG 디코딩·축소 대조와 캡처는 로딩 종료 측정 뒤 수행했으며 해당 PNG 호출은 구간 집계에 포함돼 있다.
- 최종 한 기체의 보간+그림자는 236.06+67.04=303.10MiB다. 로딩 후 프로세스 private bytes 약 556MiB, 공격 후 약 597MiB, peak working set 약 370MiB다. GPU 전체 점유나 중복 없는 전체 게임 메모리로 해석하지 않는다. 현재 전체 플레이어 모션만으로도 기체 자원 배분 검토안 256MiB를 넘으므로 1GiB 목표 달성·수백 기 달성을 확정하지 않는다.
- 최종 공격 60프레임 예열/240프레임 측정은 CPU 프레임 평균 17.77ms/p95 32.30ms, GPU draw 질의 평균 0.88ms/p95 4.54ms였다. 제한·VSync는 끄고 고정 60Hz 입력을 사용했다. 이전 360프레임·원해상도 그림자 표본과 순수 성능 개선량으로 직접 비교하지 않는다.
- I1·I2 ↔ A2·A3: [성능 목표와 잠정 검증 장비](../performance_targets.md)에 수량·부품 선택 이유·시나리오 가정·미검증을 기록했다. 페이지 상주 관리·VT·37.5%/25% 후보·실제 Iris·QHD·수백 기 성능·고주사율 제한 정책은 구현/실측 전이다.
- 실제 검증은 자동 실행·고정 입력이며 사용자 직접 조작·모든 방향/모션의 외관 검수와 최종 승인은 미검증이다. 기존 미추적 통합 소스·관련 없는 변경은 그대로 두었고 이번 변경을 섞어 커밋하지 않았다.

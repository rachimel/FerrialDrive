# 대화·개발 기록 작성 규칙

- 확정: 사용자 요청, 2026-11-04 12:48:14.865 KST.
- 적용: 새 대화 요약과 기존 기록의 회고 보완. 기록은 한국어로 작성한다.
- 목적: 누가 무엇을 왜 제안했고 누가 수용했는지, 반영 후 어떤 문제가 있었고 누구의 해결안으로 어떻게 해결했는지 추적한다.

## 필수 순서

1. 사용자가 제안한 것
2. 사용자 제안 중 AI가 수용한 것
3. AI가 제안한 것
4. AI가 제안한 것 중 사용자가 수용한 것
5. 반영 후 발견한 문제
6. 사용자 해결 제안과 실제 해결 과정
7. AI 해결 제안과 실제 해결 과정

각 제안은 `U1`/`A1`, 문제는 `I1`처럼 기록 내부 ID로 연결한다. 제안마다 내용·의도, 제시 이유, 판단 근거, 시각과 근거 출처를 적는다. 6·7에는 문제 ID, 해결 제안 주체, 제안 내용/이유, 실제 조치, 확인 결과와 남은 문제를 적는다. 공동 해결이면 두 절에 역할을 나눠 같은 문제 ID를 연결한다.

2026-11-05 사용자 후속 요청으로 위 순서의 2·3을 바꾼다. 새 기록은 이 순서를 사용하고, 기존 기록 도구도 헤딩의 의미를 기준으로 같은 순서로 표시한다. 기존 원문·식별자·보완 이력을 재작성하지 않는다.

## 사람이 읽는 서식

- 일곱 항목은 `##` 헤딩으로 구분한다. 기록 ID와 중요한 상태·결정은 굵게 표시한다.
- 새 제안은 **사용자 제안 1 (U1)**, **AI 제안 1 (A1)**처럼 의미와 추적 ID를 함께 쓴다. `scope`는 대화 전체, `U1-U3`는 사용자 제안 1~3, `I1`은 발견한 문제 1, `V1`은 확인 결과 1이다.
- 사람에게 보여주는 시각은 한국 시각(KST)으로 쓴다. UTC가 기계 원문·내보내기에 남아 있어도 화면에 중복 표시하지 않는다. 기록 시각과 보완 시각은 계속 구분한다.
- 원문은 도구의 **원문 찾기 → 선택 근거 가져오기**를 사용한다. 수동 원문 확인 버튼은 두지 않으며, 과거 원문 확인 기록은 보존한다.

## 주체와 수용 판정

- 사용자 요구를 AI가 구현했다는 이유로 AI 제안으로 바꾸지 않는다. 원래 제안자와 실제 구현자는 별개다.
- AI가 선택한 수치·알고리즘·구조는 `구현상 판단`이라고 표시한다. 이를 사용자에게 사전 제시한 제안이나 사용자가 수용한 결정으로 자동 승격하지 않는다.
- 명시 수용, 후속 정정, 거절, 잠정 시험, 확인 대기, 근거 부족을 구분한다. AI 구현 보고·사용자 침묵·시간 경과·다음 요청만으로 사용자 수용을 확정하지 않는다.
- 이유·의도가 직접 제시되지 않았으면 모른다고 적는다. 설명이 필요한 추론은 `AI의 해석 — 사용자 확인 전`으로 표시하고 사용자 발언처럼 쓰지 않는다.
- 구현 전부터 있던 문제, 반영 뒤 생긴 문제, 새 요구사항, 단순 취향 변경을 구분한다. 변경 요청을 모두 버그라고 부르지 않는다.
- 기존 요약에 의도 오해가 있으면 앞의 현재 정리에서 정정하고 원기록은 당시 판단으로 보존한다. 폐기된 해결안을 성공 사례로 남기지 않는다.

## 시간과 출처

- 한국 시간 `YYYY-MM-DD HH:mm:ss KST`로 기록한다. 원문에 밀리초가 있으면 보존할 수 있다.
- 제안·수용·문제 발견·해결 제시·구현 보고·검증·요약 작성/재정리 시각을 구분한다. 확인할 수 있는 시각만 쓴다.
- 파일명의 날짜나 수정 시각을 과거 발언·구현 시각으로 대체하지 않는다. 정확한 시각을 모르면 날짜 수준의 확인 범위와 누락 태그를 함께 남긴다.
- 대화 ID·발언 UTC 타임스탬프·짧은 검색 구절 또는 문서/커밋을 출처로 적는다. 로컬 원시 대화 파일 경로·인증정보·관계없는 대화 내용은 옮기지 않는다.
- 도구 실행 내역이나 원문 전체를 복사하지 않는다. 근거를 찾을 수 있는 짧은 발언 발췌만 사용한다. 숨겨진 추론은 기록 근거로 사용하지 않는다.

## 누락 태그와 보완

공통 접두사 `FDLOG_MISSING_`로 전체 누락을 검색한다. 형식은 `[[FDLOG_MISSING_종류:기록ID:항목ID]]`이며 항목 ID는 필요할 때 붙인다.

| 종류 | 모르는 내용 |
| --- | --- |
| TIME | 발언·수용·구현·검증의 정확한 시각 |
| SOURCE | 원문이나 직접 근거 |
| PROPOSAL | 별도 제안의 존재·내용·제안자 |
| REASON | 직접 밝힌 이유·의도·판단 근거 |
| ACCEPTANCE | 수용 여부·주체·근거 |
| PROBLEM | 문제 발견 경위·발견자·발생 시점 |
| CAUSE | 확인된 원인 |
| RESULT | 실제 조치·검증 결과·남은 문제 |

누락 태그 바로 앞에는 **무엇을 모르는지** 적고, 바로 뒤에는 **어디서 무엇을 찾아야 하는지** 적는다. `MISSING_INDEX.md`에 기록별로 묶어 보완할 필드를 확인할 수 있게 한다. 확인되지 않은 문제·제안은 `없음`으로 확정하지 않는다. 근거 있는 `해당 없음`·실제로 미수행한 항목·결정 보류는 누락과 구분한다.

보완할 때 원문 근거와 확인 시각을 추가하고 해당 태그만 제거한다. 관련 인덱스를 같은 작업에서 갱신한다. 원기록 속 당시 미확인·검증 상태는 현재 확인 결과로 덮어쓰지 않는다.

[대화 기록 도구](../../Tools/conversation_log_viewer/README.md)에서도 보완할 수 있다. 사용자 회고와 사용자의 원문 확인 표시를 구분하고 작성자·근거·당시 시각·보완 시각을 별도 기록한다. 원문 확인 표시는 사용자의 입력이며 자동 검증 결과가 아니다. 보완 이력과 원기록을 보존하고, 취소 시 인덱스를 함께 복원한다. 누락 태그는 기존 형식 보존 영역을 제외한 현재 요약에서 집계한다.

## 결과의 의미

- 기획/문서 반영, 구현 보고, 자동 검사, 화면 없는 실제 렌더링, 실제 창 조작, 사용자 승인, 커밋, 업로드를 나눠 적는다.
- 예전 검사 통과를 새 수정의 검사 결과로 쓰지 않는다. 재정리는 기존 결과의 근거를 정리하는 작업이며 프로그램을 재검증했다는 뜻이 아니다.
- 새 기록은 [_template.md](_template.md)를 따른다. 오래된 복합 주제는 과도하게 쪼개 주체를 단정하지 말고 모르는 연결을 표시한다.

# 파츠 깊이 정렬과 CPU 업로드 대조

- 기록 ID `FDLOG-20261123-part-depth-order`
- 기록일 2026-11-23 KST

## 1. 사용자가 제안한 것

- **U1** 파츠 깊이 정렬을 삽입 정렬로 바꾸고 파츠 수가 많을 때는 퀵소트를 사용한다. CPU에서 빠르게 계산한 순서도 GPU로 올린다. 요청 시각 `[[FDLOG_MISSING_TIME:FDLOG-20261123-part-depth-order:U1]]`. 대화에서 `Insertion sort로 바꾸고`와 `CPU에서 빠르게 계산하고 업로드`로 찾는다.

## 2. 사용자 제안 중 AI가 수용한 것

- 공통 색 합성 셰이더에 삽입 정렬과 반복형 퀵소트를 연결했다. 기존 깊이와 반투명 합성 규칙을 유지한다. CPU 순서 계산과 GPU 업로드 경로를 일반 파츠 사각형에서 실행할 수 있게 했다.

## 3. AI가 제안한 것

- **A1** 깊이가 같은 파츠는 원래 순서를 보존한다. 색·노멀·재질을 교환하던 루프 대신 인덱스만 이동하고, 임계값 16을 구현상 판단으로 선택했다. CPU 대조에서는 방향 재투영과 보간까지 마친 같은 깊이 표본을 받아 결과의 변수를 줄였다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- 정렬 방식은 사용자 요구를 반영했다. 임계값과 실제 깊이 읽기 방식은 구현상 판단이며, CPU를 기본값으로 변경하는 승인은 확인하지 않았다.

## 5. 반영 후 발견한 문제

- **I1** CPU 순서 정렬 자체보다 GPU 깊이 읽기 대기가 길었다. 픽셀마다 정렬할 수 있어도 순서 데이터를 위해 원본 파츠를 별도로 샘플링한다.
- **I2** 첫 대조용 실행기가 NumPy를 전투보다 먼저 가져와 기존 BLAS 설정을 우회했다. 후속 메모리 대조는 모든 경로의 `OPENBLAS_NUM_THREADS`를 1로 맞췄다.

## 6. 사용자 해결 제안과 실제 해결 과정

- **U1** GPU는 16개까지 삽입 정렬, 그 이상은 스택을 쓰는 퀵소트로 처리한다. CPU는 작은 파츠 배열에 Numba 삽입 정렬을 사용하고, 긴 배열은 깊이·원래 번호를 결합한 키로 퀵소트한다. 프래그먼트별 파츠 번호는 4개씩 32비트에 묶어 업로드했다.

## 7. AI 해결 제안과 실제 해결 과정

- 픽셀마다 깊이가 교차하거나 같은 경우, 13·17파츠에서 실제 GLSL과 CPU 업로드가 안정 정렬 기준과 일치했다. RTX 5070 Laptop FHD 30기 High와 180기 Medium의 10개 시점에서 버블·GPU·CPU 경로의 플레이어 지면·본체와 적 그림자 깊이 및 사용 타일이 일치했다. 최종 RGB는 첫 3개 캡처가 일치했고 나머지에는 일부 픽셀 차이가 남았다.
- **I1** 180기 상세 비교에서 파츠 표면 GPU 패스 p50은 버블 0.142ms와 GPU 삽입 0.137ms였다. 전체 프레임 분포의 개선은 일관되지 않았다. 별도 CPU 경로 상세 계측의 호출당 p50은 깊이 읽기·대기 0.416ms, CPU 정렬 0.027ms, 업로드 함수 경과 0.003ms였다. 업로드 수치는 GPU에서의 전송 완료 시간이 아니다. 기본은 GPU로 유지했다.
- **I2** 2GiB 제한을 적용한 180기 CPU 경로는 측정 90프레임을 완료했다. Windows Job 프로세스 커밋 최고치는 약 943MiB였다. 렌더링 테스트 36개와 1,000기 Low GPU 경로의 6프레임 실행을 확인했다. CPU 대조는 일반 파츠 사각형에 적용되며, 인스턴스 배치와 깊이 출력 전용 패스는 GPU 경로를 사용한다. Intel 재측정과 실제 17파츠 카탈로그 재생은 미수행이다.

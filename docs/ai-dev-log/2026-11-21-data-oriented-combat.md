# 교전 엔티티 저장소와 자료구조 검증

**기록 ID** `FDLOG-20261121-data-oriented-combat`

## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1)** 웹 세션에서 정리한 자료구조 개편안을 현재 코드와 대조하고, 적합하면 실제 코드에 반영한다. 확정 범위는 세대 EID·Registry·Sparse Set·컴포넌트 저장소다. 의도는 적 수백 기에서도 기존 전투·표현을 유지하면서 CPU 변환과 GPU 리소스 전달 비용을 줄이는 것이다. 대화 발언의 정확한 시각은 [[FDLOG_MISSING_TIME:FDLOG-20261121-data-oriented-combat:U1]]이다. 이 대화의 `웹세션이랑 좀 의논좀 해봤다`와 첨부한 `Ferrial Drive — Data-Oriented Architecture 및 자료구조 최적화`에서 확인할 수 있다.

## 2. 사용자 제안 중 AI가 수용한 것

- **U1** Combat Test와 이동 훈련장 실행 경로에 동일 Registry와 연속 저장소를 연결했다. 군집 이동, 양측 탄환, 관통 이력, HUD 체력 연결, 별도 `CombatWorld`의 A*, 파츠 페이지 상주 관리까지 검토했다.

## 3. AI가 제안한 것

- **AI 제안 1 (A1)** 2026-11-21 KST 구현상 판단으로, 교전 기록을 고정 폭 AoS로 보관하고 ctypes/NumPy가 같은 버퍼에 접근한다. 120Hz 서브스텝마다 생성하던 적 상태 튜플과 좌표 복사를 제거하고, 공격 이벤트 순서를 보존하기 위해 적의 삭제는 순서를 지키며 압축한다. 탄환은 발사 그룹의 순회를 유지하고 저장소는 마지막 행을 옮겨 빈자리를 채운다. 근거는 `0dcea0a`와 이 대화의 서브스텝 조사다.
- **AI 제안 2 (A2)** 2026-11-21 KST 구현상 판단으로, 두 단계 격자는 기존 Numba 균일 격자와 출현 순서·충돌 상태·시간을 비교한 뒤 선택한다. 파츠 페이지는 영구 논리 번호로 현재 GPU 슬롯 주소를 찾고, 슬롯 교체 순서의 변경은 픽셀 및 페이지 재업로드 결과를 근거로 결정한다. 근거는 비교 재생과 `d78c787`이다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- 첨부안의 세대 핸들과 컴포넌트 저장소는 명시 범위다. 행 배치, 삭제 방법, 격자와 캐시 정책은 실측에 따른 구현상 판단이다.

## 5. 반영 후 발견한 문제

- **I1** 새 뷰를 사용하면서 30기 교전의 Python 이동 경로에서 접근 비용이 증가했다.
- **I2** 페이지 키 전체를 숫자로 바꾼 첫 시험에서 슬롯 교체 순서가 달라졌고 실제 OpenGL 픽셀이 달라졌다.
- **I3** 600기 화면 벤치마크는 CPU 갱신 단축 후에도 60 FPS에 미달했다. 최종 측정에서 그리기 제출이 프레임당 평균 25.92ms였다.

## 6. 사용자 해결 제안과 실제 해결 과정

- **U1** 첨부안의 기능 동등성 기준에 따라 실제 실행 경로와 비교 재생으로 확인했다. 기체 위치, 방향, 공격 상태, 이동량, 피격 순서와 발사체 수명에 기존 상태를 대조했다.

## 7. AI 해결 제안과 실제 해결 과정

### 코드와 데이터 소유권

- `entity_storage.py`, `enemy_storage.py`, `enemy_movement_batch.py`에서 슬롯 번호와 세대로 EID를 생성한다. DenseStorage는 슬롯→행과 행→EID 대응을 관리한다. Registry의 해제는 소속 행을 지운 뒤 세대를 증가시킨다. 적이 사망해도 사망 표현과 남은 넉백에 필요한 행은 재시작 또는 직접 삭제까지 유지한다.
- 적 레코드는 위치·방향·HP·전투 단계·넉백·이동량을 소유한다. `EncounterEnemy` 공개 필드는 뷰로 접근하며 Numba는 같은 버퍼를 수정한다. Python은 공격 타이머, 명중, 발사 이벤트를 이어서 처리한다. **I1** 배열 준비비가 줄어든 경로를 8기부터 선택하도록 조정했다. NumPy/Numba가 없는 환경에는 같은 저장소를 읽는 Python 이동 경로가 있다.
- `movement_application.py`, `encounter_application.py`, `locomotion.py`, `movement_hud.py`에서 플레이어 좌표와 방향은 플레이어 Transform 행이 소유한다. 전투용 HP는 컨트롤러가 소유하고 HUD에 표시 값을 전달한다. 적과 플레이어는 같은 Registry에 등록한다.
- `projectile_storage.py`, `ranged_combat.py`, `enemy_encounter.py`에서 양측 탄환을 같은 연속 저장소에 기록한다. 적 탄환은 월드 미터, 총탄은 기존 투영 픽셀 규약을 사용한다. 발사 그룹별 시간 처리와 폭발·관통 규칙을 유지한다. 실제 교전의 관통 이력에는 표적 EID 전체를 기록하며 외부 명중 이벤트는 문자열 ID를 전달한다.
- `simulation.py`의 A*는 정적 모서리 인접 목록과 x축으로 정렬된 확장 장애물 경계를 재사용한다. 맵·충돌 반경·장애물 목록이 달라지면 재구축한다. 시연 맵 2개 벽에서 재탐색 P50 0.035→0.011ms, 48개 벽 시험에서 39.11→0.51ms였고 267개 경로가 일치했다. 첫 탐색 시간은 각각 0.056→0.079ms, 67.34→44.17ms였다. 이 값은 별도 일대일 시뮬레이션이며 군집 Steering에는 적용되지 않는다.
- **I2** `part_page_cache.py`, `part_atlas_residency.py`, `pico_part_motion.py`에서 핸들이 상주 주소를 가리키도록 바꿨다. GPU 슬롯 선택과 비동기 요청은 기존 순서를 유지한다. 추방하면 이전 핸들의 상주 주소를 지운 뒤 슬롯을 재사용한다. 페이지 파일 경로와 SHA-256은 로딩과 무결성 확인에 남긴다. 192프레임의 실제 페이지 재생 중 32개 캡처에서 픽셀이 모두 일치했다.

### 교전 CPU 재생

준비 30프레임 후 240프레임을 측정했다. 같은 프로세스에서 실행 순서를 뒤집은 두 회차의 백분위수 중앙값이다. 단위는 ms다. 30·180·600기는 12m, 900기는 4m 배치다.

| 적 수 | 기존 P50 / P95 / P99 | 적용 P50 / P95 / P99 |
| ---: | ---: | ---: |
| 30 | 0.229 / 0.384 / 0.464 | 0.103 / 0.265 / 0.373 |
| 180 | 1.079 / 1.581 / 1.902 | 0.422 / 0.789 / 0.997 |
| 600 | 3.110 / 4.122 / 4.455 | 0.982 / 1.663 / 1.831 |
| 900 | 7.225 / 11.194 / 13.908 | 3.399 / 5.313 / 5.758 |

- 600기 `tracemalloc` 최고 추적량은 약 1.21MB→0.96MB였다. 이 값의 범위는 Python 추적 할당이다. 같은 조건의 준비 시간은 두 회차 중앙값 1.8→3.8ms였다. 준비 시간에는 객체·저장소 초기화가 포함된다.
- 600기 생성의 첫 호출은 빈 JIT 디스크 캐시에서 1.72→1.80초, 캐시가 있는 새 프로세스에서 0.88→0.87초였다. NumPy/Numba 초기 로딩을 포함한다. 같은 프로세스의 두 번째 생성은 0.64~0.66→3.45~3.58ms였다.
- 두 단계 격자에서 900기 P50/P95/P99는 3.931/6.938/7.531ms였고 간격·피격 결과는 같았다. 현재 크기 분포에서는 균일 격자 경로를 유지한다. 렌더 컬링은 스프라이트 높이·사망 표시와 카메라 투영을 사용하고, 이동 격자는 생존 몸체 반경을 사용한다. 두 경로의 후보 범위와 수명을 맞추려면 추가 갱신이 필요하다.
- 20슬롯/채널, 실측과 동일한 필수 페이지 열의 오프라인 교체 비교에서 LRU 1,679회 미스·1,599회 후보 검사, 2Q 1,685회 미스·2,065회 후보 검사·최대 40개 ghost 항목이었다. 48슬롯에서는 2Q 미스가 감소했으나 현재 20슬롯에서는 LRU가 유리했다. 실제 GPU 비교에서는 두 버전 모두 1,699회 업로드·530,158,128바이트였다.

### 전체 화면

RTX 5070 Laptop GPU, FHD, 중간 PBR, 무음 자동 SMG, 12m 배치, 준비 30·측정 90프레임, 고정 시뮬레이션 60Hz, 출력 제한 해제 조건이다. 같은 장면에서 실행 간 변동이 있었다.

| 적 수 | 기존→적용 FPS | 갱신 평균 ms | 프레임 P50/P95/P99 기존→적용 ms | 프로세스 피크 커밋 MiB |
| ---: | ---: | ---: | ---: | ---: |
| 30 | 29.76→35.31 | 1.75→1.50 | 26.10/78.84/97.64→21.94/35.14/41.45 | 1429.8→1420.4 |
| 180 | 30.72→35.01 | 2.96→2.51 | 25.45/38.12/50.29→25.89/37.06/41.67 | 1357.2→1353.3 |
| 600 | 27.47→32.58 | 5.88→4.18 | 32.26/66.71/109.60→29.94/40.77/46.93 | 1376.4→1362.1 |

- **I3** 600기 마지막 프레임의 본체 배치 제출 18회, 인스턴스 업로드 35,760바이트는 동일했다. 60 FPS까지는 PBR·그림자·화면 합성의 GPU 시간과 제출 비용 검증이 남았다. Windows GPU 프로세스 메모리 카운터가 값을 제공하지 않았다. 목표 장비 i3-10100/UHD 630/RAM 4GB의 실측과 직접 조작 검증은 미수행 상태다.
- 효과 경로는 현재 GPU 인스턴스 배치와 개별 시간표를 유지한다. PBR 방향 상주의 별도 `AtlasTextureCache`는 페이지 풀 교체 시험과 다른 경로이며 현행 정책을 유지한다.

실행 경로는 `tests/combat_test_v1_5.py`, `tests/combat_test_v1_5_speed_test.py`, `tests/sword_movement_test.py`, `tests/hardware_profile_benchmark.py --scenario combat`이다. 원자료와 재생 스크립트는 로컬 `output/performance/data_oriented/`의 `before/`, `final/`, `paired_cpu.json`, `routing.json`, `paged_atlas.json`에 있다.

### 검증 결과

- 변경 전 코드와 30·180·600·900기, 270프레임씩 대조했다. 각 프레임의 적 HP·좌표·방향·이동량·공격 상태, 발사체 수명과 명중 이벤트가 일치했다.
- UTF-8 모드의 전체 자동 검사 1,171개 중 1,087개가 통과했고 84개가 생략됐다. 새 검사는 세대 재사용, 행 이동·확장, 외부 해제, 관통 이력과 지도 변경을 다룬다.
- 파츠 아틀라스 선택 GPU 검사 24개가 통과했다. 적 렌더링 선택 GPU 검사 13개 중 두 개가 실패했다. 변경 전 코드에서도 `test_overlap_preserves_order_and_each_interpolation_phase`의 소형 Break 최대 차이 20과 `test_deferred_depth_skips_covered_tile_pixels_and_preserves_blending`의 최대 차이 1을 재현했다.

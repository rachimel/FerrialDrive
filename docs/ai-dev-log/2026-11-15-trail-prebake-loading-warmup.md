# Trail 결 사전 파일과 로딩 중 셰이더 준비

- **기록 ID:** `FDLOG-20261115-trail-prebake-loading-warmup`
- 작성 범위: 2026-11-15 현재 대화·현행 코드·실제 OpenGL 첫 공격 비교. 사용자 개별 발언 시각은 미확인: `[[FDLOG_MISSING_TIME:FDLOG-20261115-trail-prebake-loading-warmup:scope]]`. 검색 단서: `첫 공격 때만`, `결 텍스처는 미리 파일로`, `셰이더도 로딩 중에 준비`, `첫 공격 끊김 없어지는지도`.
- 확인 시각: CPU 생성 측정 15:11:21 KST, 수정 전 실제 게임 15:15:25 KST, 수정 후 15:23:08/15:28:01 KST. 기록 정리 15:30 KST 이후. 요청 발언 시각과 구분한다.
- **상태:** 준비 도구·로더·로딩 연결 구현, 로컬 게임/시연 파일 생성, 자동 검사·실제 GL·첫 공격 비교 완료. 물리 입력·최소 사양 실기·모든 드라이버의 콜드 캐시·장기 실행·커밋·업로드와 구분한다.

## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1):** Trail을 미리 Baking할 수 있는지 물으며 그릴 때 약간 멈춘다고 보고했다. 진단 질문에는 `첫 공격 때만`이라고 답했다. 발생 패턴을 사용자 보고로 기록하며 측정 전부터 원인이 확정됐다고 쓰지 않는다. 시각·출처는 scope를 따른다.
- **사용자 제안 2 (U2):** 결 텍스처를 미리 파일로 만들고 셰이더를 로딩 중 준비하며 첫 공격 끊김이 없어지는지 확인하도록 명시 요청했다. 동작 전체 Baking보다 고정 결·초기 준비를 분리하는 요청이다. 시각·출처는 scope를 따른다.

## 2. 사용자 제안 중 AI가 수용한 것

- U1: 상시 계산과 첫 사용 준비를 구분해 조사했다. 픽셀 생성 자체와 실제 게임의 첫 Trail 프레임을 따로 측정했다.
- U2: 원래 결 생성기는 제작 기준으로 보존하고, 실행에서는 검증한 준비 파일만 읽는다. 로딩 단계에 Compute·Vertex·Fragment 컴파일, 제어점/job/출력 SSBO 예약과 별도 작은 대상의 GPU 첫 실행을 연결했다.
- GPU 미지원의 기존 CPU 경로와 게임 에셋 없는 `--demo`를 보존했다. 시연은 자체 생성 경로를 사용하며 기존 게임 `data/`의 이미지를 필수로 요구하지 않는다.

## 3. AI가 제안한 것

- **AI 제안 1 (A1), 진단 판단:** 첫 공격만 멈추면 고정 궤적 전체 Baking 전에 지연 생성·컴파일을 확인한다. 실제 첫 draw 안에 결 생성과 프로그램 생성이 있었기 때문이다. 근거는 `PicoSwordEffects.draw_trail/prepare_flow`, 수정 전 기록이다.
- **AI 제안 2 (A2), 구현상 판단:** 표준 ZIP에 manifest·RGBA8을 저장하고 설정·크기·SHA-256을 확인한다. 기존 픽셀의 바이트를 유지하고 Pillow·SDL 디코더 의존 없이 제작·로드하기 위해서다. 준비·실행 진입점은 `automate/run.py trail-texture`와 `ferrial_drive/assets/trail_flow.py`다.
- **AI 제안 3 (A3), 구현상 판단:** 컴파일 성공만으로 끝내지 않고 별도 8×8 렌더 대상에서 Compute·그리기를 실행한 뒤 완료를 기다린다. 드라이버의 지연 준비와 초기 SSBO 할당도 공격 밖으로 옮기기 위해서다. 게임 공격·명중 상태를 가짜로 진행시키지 않는다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- U2가 결 파일·로딩 준비·첫 공격 확인을 명시 승인했다. ZIP 형식·파일 키·예약 크기·작은 렌더 대상·시험 프레임 수는 AI의 세부 구현 판단이며 별도의 사용자 확정 수치로 확대하지 않는다.
- 이번 요청은 결 외관 변경이나 전체 Trail 동작을 이미지로 Baking하는 승인이 아니다. 모션·판정·색·결 생성 수식은 유지했다.

## 5. 반영 후 발견한 문제

- **I1, 기존 원인 확인:** 512×128·18가닥 결 픽셀 생성만 CPU 3회 약 336.9/335.0/336.7ms였다. 수정 전 실제 첫 Trail 프레임은 372.5ms이며 그 안에서 결 생성 약 353.0ms, Compute 컴파일 약 1.11ms를 확인했다. 반복 공격에는 생성·컴파일이 없었다.
- **I2, 검증 한계:** 수정 후에도 60FPS 예산을 넘는 일반 프레임이 있다. 첫 공격의 수백 ms 준비 지연과 전체 60/165FPS 목표를 구분한다. 같은 PC의 숨김 창·고정 입력이며 실제 UHD 630 성능은 측정하지 않았다.
- **I3, 화면 대조 범위:** 전후 공격 완료 캡처는 Trail·기체·월드 영역이 같았지만 HUD의 작은 자원 표시 영역에서 833/821픽셀이 달랐다. 영역은 첫 공격 `[691,997,736,1051]`, 반복 `[690,1000,736,1050]`이다. 차이 원인은 특정하지 않았다: `[[FDLOG_MISSING_CAUSE:FDLOG-20261115-trail-prebake-loading-warmup:I3]]`. 검색 단서: 전후 `first_attack.png`·`repeat_attack.png`, `UiV2View.resources/ultimate_icon`과 HUD 표시 상태. 전체 화면이 바이트 일치했다고 보고하지 않는다.

## 6. 사용자 해결 제안과 실제 해결 과정

- I1 ↔ U2: 게임 로컬 `data/effects/sword_trail/`와 시연 자체 `samples/sword_movement/generated/trail_flow/`에 준비 파일을 생성했다. RGBA는 262,144바이트이며 두 파일의 원본 픽셀 SHA-256은 `ecc0f69a27e7e5cc07b32d6a786d9649f640287130f18b442ae2d3f6ce5f2e42`다. 압축 파일은 각각 33,932바이트다.
- 준비 파일은 설정·생성기 버전별 키를 사용한다. 정상 기존 파일은 재사용하고 미준비·손상·다른 설정은 오류로 알린다. 런타임의 느린 픽셀 생성 fallback은 넣지 않았다. 생성물은 Git 제외를 확인했다.
- 훈련장 `Trail 준비` 단계에서 자원을 준비한다. 공통 TimingRecorder의 `loading.sword_trail.prepare`로 포함 비용을 선택 기록한다. 화면·배율·viewport·clip·SSBO와 GL 상태는 복원하고 임시 대상은 해제한다.

## 7. AI 해결 제안과 실제 해결 과정

- I1 ↔ A1/A3: 실제 게임을 새 프로세스로 열고 idle 60프레임 뒤 첫 공격 180/반복 공격 180프레임을 고정 1/60초로 진행했다. FHD·저장 품질 low·VSync/프레임 제한 없음·숨김 GL 창 조건이다. CPU 구간 계측이며 GPU 전용 시간을 뜻하지 않는다.

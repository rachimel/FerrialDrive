- **I1, 기존 사용감 문제:** U1의 즉시 회전·달리기/대시 방향 기준 불일치. 코드에서 달리기는 이동 벡터, 대시는 조준 벡터를 즉시 `facing`에 대입하는 것을 확인했다. 발견 시각은 scope 참조.
- **I2, 기존 시작 지연:** U4가 첫 화면 표시 전 지연을 제보했다. `runtime.run_application()`은 `program.enter()`가 끝난 뒤 첫 draw/present를 실행한다. 초기화에서 일반 시트와 이동·공격 보간 전체를 순차 준비한다. 어느 구간이 실제 지연의 몇 %인지 아직 측정하지 않았다.

## 7. AI 해결 제안과 실제 해결 과정

- I2 ↔ A3, **현행 소스 조사:** 일반 본체/그림자 시트를 먼저 로드하고, `PicoMotionSprite`가 모든 클립의 PNG·원시 벡터를 읽어 `set_clip()`으로 텍스처 4장을 준비한다. 색상은 `premultiply_rgba()`의 Python 픽셀 반복문으로 런타임 변환한다. 클립 내부 PNG 공유는 이미 한 번만 디코딩한다. 클립 간·일반 시트/보간 경로 간 중복 제거 효과는 별도 확인 대상이다.
- **현재 메타데이터 집계:** 이동 128클립/704구간과 공격 32클립/208구간. 참조 파일 합계 3,968개 중 PNG 1,072개, 파일 크기 합계 약 799.3MiB다. 4개 RGBA 텍스처의 계산상 페이로드는 약 1,497.9MiB, 런타임 알파 사전 곱셈 대상은 약 1.964억 픽셀이다. 일반 시트·UI·GPU 드라이버 추가 비용은 제외하며 RAM/VRAM 실측이나 시작 시간 측정값이 아니다.
- **병목 후보:** Python 픽셀 변환과 대량 순차 준비가 유력하지만 전체 시간의 지배 구간으로 확정하지 않는다. 기존 이동 `--profile`은 update/draw와 화면 표시/대기를 기록하며 초기 로딩 내부 구간은 계측하지 않는다. 다음 분석에서 시작→첫 화면 표시와 시작→조작 가능, 각 준비 구간을 나눠 측정한다.
- **병렬화 범위:** 파일 읽기·디코딩·CPU 준비와 GPU 텍스처 생성/전송을 분리한다. SDL2 렌더 API는 메인 스레드 호출 대상이므로 기존 GPU 로딩 함수를 그대로 작업 스레드에 보내는 방식은 적용하지 않는다. 근거: [SDL2 렌더 API](https://wiki.libsdl.org/SDL2/CategoryRender).
- **압축 범위:** 저장 용량 압축과 GPU 텍스처 압축을 구분한다. 현행은 `SDL_PIXELFORMAT_RGBA32` 텍스처를 생성한다. 벡터는 RG/BA에 signed16 고정소수점 수치를 담으므로 색상 이미지용 손실 압축을 그대로 적용하면 안 된다. 원본은 보존하며 압축 정책·Pico2D 연결 가능성·실제 크기 화질은 별도 검토한다.
- 확인: 읽기 전용 소스 조사와 메타데이터 집계, 명세 일관성 확인. 코드·에셋·사용자 실행 창은 변경하지 않았고, GUI 실행·구간별 시간 측정·실제 개선·시각 검증·커밋·업로드는 하지 않았다.

## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1):** 기존 애니메이션 제작 파이프라인을 보류하고 Unreal에서 AI가 제작한 애니메이션을 사용자가 수정하는 안을 고려한다.
  - 의도: AI 제작과 사용자 직접 수정의 역할을 검토한다. Unreal 채택 확정 요청은 아니다.
  - 별도의 도구 변경 이유는 직접 제시되지 않았다 — [[FDLOG_MISSING_REASON:FDLOG-20261110-unreal-animation-review:U1]] 현재 발언 전후의 이유 설명을 확인한다.
  - 시각·출처: 위 대화 범위와 사용자 발언.
- **사용자 제안 2 (U2):** “한 번 실험해보자”, Blender 모델을 Unreal로 포팅하고 Unreal MCP로 AI가 rough 편집 → 사용자 수정 → blend 반환을 시험한다. Unreal은 이미 설치됐다고 알렸다.
  - 의도·근거: 제안한 제작 방식의 실제 왕복을 확인한다. 전체 게임 엔진 변경·정식 파이프라인 채택 요청은 아니다.
  - 시각·출처: 현재 대화의 위 발언. 정확한 시각은 scope 항목에 포함한다.

## 2. 사용자 제안 중 AI가 수용한 것

- **U1 수용:** 기존 파일을 보존하고 제작 흐름 문서에 보류 상태를 표시한다. 새 안은 검토 단계로 기록하며 Unreal 채택·설치·리그 변경은 확정하지 않는다.
- 수용 근거: 이번 AI 응답. 정확한 시각은 scope 누락 항목에 포함한다.
- **U2 수용:** 원본을 보존하고 로컬 실험 프로젝트에서 실행한다. 최신 기본 파일 `base_pose.blend`의 해시 `d84ab62…315c56`을 확인했다. Unreal 5.8.0과 Blender 5.2.3 LTS를 실제 확인했다.
- 후속 사용자 보고: “Enter 누르면 적용되네. 일단 대충 테스트는 되는듯?”라고 입력 반영과 초기 조작 결과를 알렸다. AI는 U2의 남은 단계인 수정본 반환을 진행했다. 조작법의 보편적 규칙이나 최종 채택 승인으로 확대하지 않는다.

## 3. AI가 제안한 것

- **AI 제안 1 (A1, 독립 제안):** Control Rig를 공통 편집 대상으로 삼아 AI가 포즈·키를 작성하고 사용자가 Sequencer에서 수정한다. 편집 가능한 원본과 출력용 베이크 결과를 구분하고, AI 재작업 시 사용자 수정분의 보존 규칙을 정한다.
  - 이유·근거: Epic 공식 문서가 Control Rig 트랙 생성·컨트롤 키 설정 등의 Python 자동화와 Sequencer 애니메이션 제작을 설명한다. 이 기능을 AI 제작 경로에 활용할 수 있다는 판단이며 현재 환경에서의 성공 증거는 아니다.
  - [Control Rig 애니메이션 Python 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-scripting-for-animating-with-control-rig-in-unreal-engine), [Animation Sequences](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-sequences-in-unreal-engine).
- **AI 제안 2 (A2, 독립 제안):** 짧은 동작 하나로 AI 키 작성 → 사용자 직접 수정 → 저장·재개 → 기존 Pico2D용 출력 경로 연결을 시험한 뒤 채택 여부를 판단한다. 실제 Unreal 버전·연결 방법과 출력 경로는 시험 전 확인한다.
  - 이유·근거: 도구 변경만으로 관절축·강체 장갑 간섭이 해결되지는 않는다. 초기 Control Rig 구성 비용, 수동 수정 편의, 사용자 수정 보존, 출력 호환성이 핵심 검증 대상이다.
  - 제안 시각·출처: 이번 AI 검토 응답. 정확한 시각은 scope 누락 항목에 포함한다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- 최초 검토 시 A1·A2는 **사용자 확인 대기**였으며 당시 구현·시험·도구 채택 승인을 추정하지 않았다.
- 후속 U2로 A1의 AI 제작/사용자 편집 방식과 A2의 짧은 동작 실험을 **잠정 시험**으로 수용했다. 이번 반환 목적지는 사용자 지정대로 blend다. Pico2D 연결까지 수용·검증한 것으로 확대하지 않는다.
- Undo 발견 후 사용자에게 편집 중인지 확인했고, 사용자는 “지금은 AI가 초안 제작을 계속해”라고 답했다. 이후 “언리얼 조작이 처음이라 자꾸 이상한거 움직인다 내가”라고 설명했다. 초안 최종 승인이나 사용자 수정 완료 응답은 아직 아니다.

## 5. 반영 후 발견한 문제

- 최초 검토 때는 기본 Python 실행 오류와 MCP 미연결로 상태를 확인하지 못했다. 이번 실행에서는 명시한 Python으로 준비하고 설치·호스트 연결을 확인했다.
- **문제 1 (I1):** 제한된 실행에서 Unreal 캐시·MCP 작업 기록 경로 초기화에 실패했다. 실험 캐시 경로를 명시하고 실험용 호스트만 일반 사용자 권한으로 시작했다.
- **문제 2 (I2):** Interchange의 FBX 가져오기 시작 이후 진행이 멈추고 요청이 시간 초과됐다. 저장된 에셋이 없는 상태를 확인했다. 기존 FBX 경로로 바꾼 다음 실제 Skeletal Mesh 가져오기가 완료됐다. Interchange 정지의 내부 원인은 확정하지 않는다.
- **문제 3 (I3):** FK 트랙 생성 직후에는 제어점이 초기화되지 않았다. 이후 틱에서 71개 제어점 생성이 확인돼 생성·키 작성 단계를 나눴다. 중간 Undo로 트랙이 제거된 것은 사용자에게 확인한 뒤 복구했다.
- **문제 4 (I4):** 예상한 일부 Unreal Python 메서드가 5.8에 없었다. 설치된 헤더·실제 MCP introspection을 기준으로 경로 조회, 본 조회, 뷰포트 카메라 API를 보정했다.
- **표시 한계:** Unreal 재질이 단순화됐고 FBX에서 패킹 이미지 2개의 디스크 경로 누락 경고가 있었다. 원본 Blender의 116개 패킹 이미지 보존 확인과 구분한다.

## 6. 사용자 해결 제안과 실제 해결 과정

- I3: 사용자가 AI 계속 진행을 명시했고, 조작 미숙으로 물체를 잘못 움직였다고 설명했다. AI가 초안을 계속 작성하고 직접 수정은 준비 완료 후 안내하기로 했다. 이 인계 당시에는 사용자 수정이 미수행이었다.
- 후속 직접 조작: 사용자가 Enter로 입력값이 반영됐다고 보고했다. AI가 키를 읽어 0·15·30프레임의 `chest_CONTROL` Yaw가 0→28→0도임을 확인했다. AI 초안의 중앙 키 8도에서 바뀐 것을 근거로 사용자 수정 단계가 실제 진행됐음을 구분했다. 정확한 조작 시각·반영 전 입력 과정은 scope 누락 항목에 포함한다.

## 7. AI 해결 제안과 실제 해결 과정

- I1~I4: DCC-MCP 스킬에 따라 공식 CLI 0.20.53을 체크섬 검증 후 output에 배치했다. 공식 어댑터 wheel 0.3.0의 카탈로그 해시를 검증했고 Core 0.20.53과 함께 실험 workspace에 설치했다. 엔진 설치 폴더는 변경하지 않았다. `dcc-mcp-production-reuse/v1` 가이드를 읽고 검증 helper를 통과했다.
- 재사용 조사: 기존 모듈·DCC-MCP Marketplace의 `unreal animation`, 공식 Control Rig/Fab 후보와 upstream 어댑터를 확인했다. 번들 템플릿은 Godot 전용이며 현재 작업에 맞지 않았다. UE 전용 Mannequin 에셋은 이번 Blender 반환에 도입하지 않았다. 기존 사용자 모델과 네이티브 FK Control Rig를 사용하고 누락된 키 편집/베이크 기능만 로컬 MCP 스킬로 추가했다. 외부 에셋 구매·다운로드는 하지 않았다.
- `Tools/unreal_pipeline/blender_transfer.py`는 평가된 형상·본의 FBX 사본, 본 이름 매핑, 원래 리그로 반환, 재로딩 비교를 담당한다. `skills/mech-animation-lab`은 고정 실험 범위의 생성·키 작성·편집 화면 준비·FBX 출력을 담당한다.
- 실제 메카 417개 메시·69개 원래 본을 교환용 사본으로 출력했다. Unreal에는 루트 2개를 포함해 71개 본이 표시됐으며 원래 69개 본을 반환 매핑했다. 원본 해시는 유지됐다.
- `/Game/MechLab/RoughTorso`의 `chest_CONTROL`에 0·15·30프레임의 로컬 Yaw 0→8→0도를 작성하고 실제 조회 값도 확인했다. 현재 본 축에서는 상체 기울기로 보인다. 게임 모션 사양이 아닌 1초 연결 시험이다.
- 실제 MCP 호출로 FBX를 베이크·출력하고 `return/rough_torso.blend`에 `Unreal_RoughTorso` Action을 연결했다. 31개 정수 프레임·2개 중간 시각 × 69개 본, **2,277개 표본**의 저장/재로딩 비교에서 최대 위치 오차 약 **3.12e-6 리그 단위**, 회전 오차 약 **5.42e-7 rad**였다. 최초 보고의 2π 값은 같은 방향인 쿼터니언 부호를 포함한 지표였으며 정규화한 독립 재로딩 검사로 구분했다.
- 원본/반환의 객체 525개 구조 지문과 패킹 이미지 116개 해시가 일치했다. 기존 회전 모드와 4개 Pose Constraint를 유지했다. 이 구조 지문은 전체 데이터 동등성·전 모션 안전성을 증명하지 않는다.
- 시각 확인: 교환 사본 6면, 반환 15프레임 6면의 확대·240px, 반환 사선 재질 렌더 640px·240px와 실제 Unreal 뷰포트를 AI가 열어 확인했다. 누락·분리된 주요 부품이 보이지 않았고 반환 파일에서 원래 회색 재질·청색 발광을 확인했다. 전체 연속 간섭·모든 자세·Unreal 재질 이식·사용자 사용감·Pico2D 재생은 미검증이다.
- 공개 가능한 두 본·두 상자 샘플도 실제 공통 경로로 생성·FBX 출력했다. 샘플의 독립 Unreal 수동 왕복 시연은 미검증이다. MCP 스킬 lint는 1개 도구 계약에서 오류·경고 0개였고 Python AST 검사도 통과했다.
- 최초 인계: 실제 MCP에서 15프레임과 `chest_CONTROL` 선택 상태를 확인했다. 당시에는 사용자 수정본을 반환하기 전이었다.
- `model_review.py`로 반환 후보의 14개 이미지 근거와 AI 판단을 기록했다. 검토 상태는 `awaiting_user`, `stage_approval=false`다. 사용자 수용을 대신 기록하지 않았다.
- 사용자 수정 반환: 키 값 0→28→0도를 확인한 뒤 `UserTorso_Baked`와 `return/user_torso.fbx`를 새로 출력했다. 이를 원래 리그에 `Unreal_UserTorso` Action으로 연결해 **`return/user_torso.blend`**로 저장했다. 원본과 기존 AI 초안 반환본을 덮어쓰지 않았다.
- 수정본 재로딩: 2,277개 본 표본에서 최대 위치 오차 약 **2.42e-6 리그 단위**, 회전 오차 약 **4.88e-7 rad**였다. 원본 해시는 유지됐다. 객체 525개의 구조 지문·패킹 이미지 116개 해시도 원본과 같았고 기존 회전 모드·4개 Pose Constraint를 유지했다.
- 수정본 이미지: 15프레임의 6면 확대·240px와 재질 사선 640px·240px를 AI가 직접 열어 사용자의 더 큰 상체 굽힘과 손발·무기 연결, 원래 재질을 확인했다. 사용자 수정 각도를 AI가 고치지 않았다. 해당 포즈의 전체 장갑 간섭·연속 동작 품질 승인은 별도다.
- 반환 보고서는 요청의 사용자 수정 상태를 기록하도록 보정했다. 새 파일에 사용자의 확인된 수정을 미수행으로 고정 기록하지 않는다. 이 변경과 실제 수정본 반환 경로를 함께 확인했다.
- 다음 판단: AI 초안→사용자 직접 수정→blend 반환의 연결 시험은 한 차례 완료했다. 작업 편의·IK 제어 필요·실제 전투 동작 제작 품질은 후속 검토 범위이며 정식 채택을 확정하지 않는다.

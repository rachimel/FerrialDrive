## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1):** 모델 렌더부터 애니메이션 조립·2D 스프라이트 제작을 연결하고 SSheetCutil을 참고한다. 상단 조작줄의 여백을 줄이고 제목 강조는 글자 크기로 처리한다.
  - 이유·근거: 기존 UI의 불필요한 설명과 버튼 위주 구성에 대한 앞선 지적에 이어 제작 흐름과 구체적인 배치를 요청했다.
- **사용자 제안 2 (U2):** 리그도 고려 중이다.
  - 이유·근거: 조립 범위가 2D 프레임 편집인지 3D 리그/동작 제작까지인지 확인한 질문에 답했다. 리깅 편집 UI의 즉시 구현을 확정한 것으로 해석하지 않는다.

## 2. 사용자 제안 중 AI가 수용한 것

- 기존 Blender 렌더·SSheetCutil 호환 패킹을 연결하고 프레임 순서·반복·FPS·피봇을 편집한다. 기존 리그·활성 동작·키프레임을 유지해 렌더한다.
- 상단 조작줄은 y=64, 제목은 28px로 조정하고 미리보기 영역을 위로 확장한다. 앞서 제거한 부가 문구를 다시 추가하지 않는다.

## 3. AI가 제안한 것

- **AI 제안 1 (A1), 구현 판단:** 상단 제작 메뉴와 설정/조립 입력창을 분리한다. Blender 작업은 별도 프로세스, 공통 게임 로더는 기존 모듈에 유지한다.
  - 이유·근거: 큰 작업 버튼을 추가로 나열하지 않고 기존 처리·프로세스 정리를 재사용한다.
- **AI 제안 2 (A2), 구현 판단:** 본체/그림자 동시 조립·선택한 동작의 기본 방향 대응·새 폴더 저장을 적용한다. 리깅/스키닝/리타기팅 편집 UI는 후속 범위로 둔다.
  - 이유·근거: 레이어 불일치와 입력 덮어쓰기를 막고, 리그 검토를 자동 리깅 완료로 과장하지 않는다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- U2는 리그 고려를 명시했으나 A1/A2의 구체적인 입력창·저장 방식·수치에 대한 별도 사용 승인은 받지 않았다. 구현상 판단과 사용자 수용을 구분한다.

## 5. 반영 후 발견한 문제

- **발견한 문제 1 (I1):** 새 이름으로 조립한 동작을 저장해도 기존 시트 첫 동작이 미리보기에 선택될 수 있었다. 번들의 방향 대응과 기본 재생 동작을 함께 연결해야 했다.
- 실제 기체의 모든 리그·NLA·제약·애니메이션과 파일 선택/드래그 사용감을 검증한 것은 아니다. 기본 도형의 단일 본 경로와 구분한다.

## 6. 사용자 해결 제안과 실제 해결 과정

- U1의 기존 시트 도구 참고 지시를 따라 v1 JSON·bottom-left 영역·피봇·동작별 FPS와 기존 패킹을 재사용했다. I1에 대한 별도 사용자 해결 제안은 없었다.

## 7. AI 해결 제안과 실제 해결 과정

- 저장 장면의 모델 계층 위에 렌더용 부모를 추가해 방향을 회전하고 기존 리그/키프레임을 보존한다. 필요하면 카메라·광원·ShadowCatcher를 준비하며 원본 대신 별도 작업본을 저장한다.
- 조립은 방향별 프레임 순서·반복·FPS·피봇을 레이어에 함께 적용하고 새 폴더에 이미지와 JSON을 저장한다. 입력 파일과 기존 결과를 덮어쓰지 않는다. 조립창에는 본체 재생 미리보기를 제공한다.
- I1: 기본 방향 대응·공통 자원의 기본 동작·저장 후 선택 동작을 연결했다. 재개봉 검사를 추가했다. 수정 전 생성된 검증 출력도 다시 조립해 현재 규격으로 확인했다.
- 자동 44개 통과: 기존 로더 26개·패킹 8개·제작/조립 10개. 실제 Tk 입력창은 숨긴 창에서 입력·순서·저장 경로를 검사했으며 사람의 직접 조작 확인과 구분한다.
- 공개 가능한 단일 본·스키닝·키프레임 도형을 실제 Blender에서 8방향 × 2프레임 × 2레이어로 렌더했다. 본 애니메이션에 따른 PNG 변화·원본 .blend 해시 보존·패킹·조립·Pico2D 표시를 확인했다. 수정된 상단과 제작 메뉴는 SDL dummy 캡처로 확인했다.
- 게임 에셋·생성 .blend·렌더 출력·작업본은 추적하지 않는다. 공통 FDrive는 Blender·제작 화면에 의존하지 않는다.

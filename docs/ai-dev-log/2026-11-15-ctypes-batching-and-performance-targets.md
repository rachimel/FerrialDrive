## 1. 사용자가 제안한 것

- **사용자 제안 1 (U1):** ctypes의 성능 개선 가능성과 DLL 사전 로드를 확인한다. Python 전반의 비용과 PyPy 검토에 이어 호출 경로의 비용을 조사하는 요청이다. 제안 시각·출처는 scope를 따른다.
- **사용자 제안 2 (U2):** 최소 사양은 약 16.66ms, 권장 사양은 약 6.06ms를 목표로 한다. 60FPS·165FPS 예산으로 구분했다. 개별 프레임 예산을 지키는 개발 목표이며 현재 달성 보고가 아니다. 제안 시각·출처는 scope를 따른다.
- **사용자 제안 3 (U3):** RAM 4GB를 제시한 뒤 `RAM은 8GB로 동일`로 정정했다. 현재 최소 사양 RAM은 8GB다. 이 발언으로 권장 부품이나 권장 RAM을 별도 확정하지 않는다. 제안·정정 시각·출처는 scope를 따른다.

## 2. 사용자 제안 중 AI가 수용한 것

- U1: 제품 코드를 바꾸지 않고 SDL DLL 로드·GL 함수 연결·구조체 생성·호출 단위를 확인했다.
- U2/U3: 기존 i3-10100·UHD 630·RAM 8GB·SSD 256GB 검증 기준을 FHD 최소 60FPS에 연결했다. 권장은 FHD 165FPS이며 구체적인 장비는 미정이다. 현재 기준 문서와 샘플 프로필의 기본 `target_fps`를 60으로 맞췄다.
- 60FPS의 정확한 예산은 16.666…ms이며 문서에는 약 16.67ms로 표기했다. 165FPS는 6.0606…ms다.

## 3. AI가 제안한 것

- **AI 제안 1 (A1), 조사상 판단:** 정점 구조체 재사용과 링의 묶음 제출을 별도로 반복 측정한다. DLL 로드 비용과 프레임별 데이터 준비·외부 함수 호출 비용을 혼동하지 않기 위해서다. 현재 대화의 조사 진행 보고와 14:27 KST 실험 결과가 근거다.
- **AI 제안 2 (A2), 문서 반영 판단:** 평균 외에 p95/p99·예산 초과 횟수를 기록하고 측정 구간 전체에서 예산을 지키는 것을 목표로 명시한다. 권장 부품은 측정 전 임의로 확정하지 않는다. U2를 반영한 기준이며 최적화 구현 제안과 구분한다.

## 4. AI가 제안한 것 중 사용자가 수용한 것

- U1~U3의 조사·목표·RAM 정정은 명시 요청이다. A1의 후보 방식·캐시 정책·실제 제품 적용이나 SDL 배칭 강제 활성화에 대한 별도 승인은 요청하거나 확정하지 않았다.
- 사용자의 `ㅇㅎ`를 제품 최적화 완료나 해당 구현 방식의 최종 승인으로 확대하지 않는다.

## 5. 반영 후 발견한 문제

- 제품 렌더링을 수정하지 않았으므로 아래는 기존 경로에서 조사한 비용·주의점이다.
- **I1:** SDL DLL은 PySDL2 import 시 로드하고 함수별 `argtypes`·`restype`를 설정해 재사용한다. 주요 GL 함수도 렌더러 생성 시 연결해 인스턴스 속성에 보관한다. DLL 사전 로드만으로 반복 호출 비용이 사라지지 않는다.
- **I2:** `PicoV2Renderer.filled_triangle()`은 매 호출마다 SDL_Vertex·FPoint·Color와 배열을 새로 구성한다. `PicoRenderer.ring()`은 캐시한 수평 span마다 별도 `SDL_RenderDrawLine`을 호출한다.
- **I3:** 전체 경로에 배칭이 없지는 않다. Trail mesh의 묶음 제출, Compute/Instancing 경로, Bicubic 상태 저장·복구 범위가 있다. Bicubic의 `batch()`는 모든 사각형을 하나의 draw call로 합치는 기능이 아니다.
- **I4:** SDL 내부 자동 배칭은 지원 여부와 활성 여부를 구분해야 한다. 현행 캔버스는 OpenGL 드라이버를 명시한다. 확인한 SDL 2.32.10 소스는 명시 드라이버 선택 시 기본 배칭을 끄며 hint/백엔드 설정으로 달라질 수 있다. 실제 게임 GL 렌더러의 활성 상태·GPU draw call 수는 이번에 측정하지 않았다.
- **I5:** 전역 `git diff --check`는 기존 다른 개발 로그의 공백 오류를 보고했다. 해당 파일은 수정하지 않았으며 이번 대상 파일의 검사는 별도로 수행한다.

## 6. 사용자 해결 제안과 실제 해결 과정

- I1 ↔ U1: DLL 사전 로드는 이미 사용하는 구조임을 확인했다. GL 함수 주소는 Windows에서 유효한 GL context 생성 후 연결하고 context 수명에 맞춰 관리해야 한다. 초기 로드 시점을 옮기는 것과 정상 플레이의 호출 비용 감소를 구분했다.
- U2/U3: PRE-PRD·성능 목표·벤치마크 사용법·시연 설명을 동기화했다. 최소 프로필은 RAM 8GB·60FPS다. 일반 게임 60FPS 기본값과 프로세스/Job 1GiB 커밋 제한은 유지한다. 커밋 제한은 PC 전체 RAM 8GB의 에뮬레이션이 아니다. 기존 165FPS 원시 결과는 변경하지 않았다.

## 7. AI 해결 제안과 실제 해결 과정

- I2 ↔ A1: 게임과 같은 Python 3.11.16에서 공통 TimingRecorder로 반복 측정했다. 정점은 회차당 10,000회×7, 링은 200회×7이며 예열을 제외하고 회차별 평균의 중앙값을 비교했다. timeit 측정 루프는 기본 GC 비활성 조건이다.
- 삼각형 3정점 준비는 기존 생성자 구성 약 13.67μs, 버퍼와 하위 구조체 view 재사용 약 1.36μs였다. 결과 메모리 바이트는 일치했다. 좌표·색·UV 작성만의 비용이며 SDL 제출·게임 FPS 결과가 아니다.
- 반지름 82·두께 6의 링은 수평 span 328개다. SDL 소프트웨어 렌더러에서 기존 328회 선 호출 약 241.53μs, 고정 사각형 버퍼의 1회 제출 약 14.80μs, x/y를 매번 갱신한 뒤 1회 제출 약 39.03μs였다. flush까지 포함했으며 제품의 OpenGL 경로로 성능 배율을 환산하지 않는다.
- 정수/소수점 중심·불투명/반투명 4조건에서 링의 출력 픽셀은 일치했다. 스케일·회전·클리핑·실제 GL 드라이버·전체 UI 순서·사용자 외관은 미검증이다. 새 배칭이 투명 도형의 순서를 바꾸지 않도록 별도 검증이 필요하다.
- I3/I4: 우선순위는 반복 데이터 생성과 Python→외부 함수 호출 단위다. SDL 내부 배칭은 앞단 ctypes 호출을 없애지 않는다. GL 전환 전 flush와 상태 복구가 필요하므로 자동 배칭만 무조건 켜는 변경은 하지 않았다.
- 검증: 기존 hardware profile 자동 검사 13개 통과·실제 GPU 선택 검사 1개 생략. 최소 60/권장 165 각각의 예산 직전·직후 판정, 프로필 JSON과 진입점 구문을 확인했다. 제품 최적화·최소/권장 실기 FPS·수백 기 전투·새 전체 게임 실행은 미수행이다.
